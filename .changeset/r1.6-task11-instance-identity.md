R1.6 Task 11 — instance identity: read existing records, rank, human decides

At review, each dictated collection instance is shown alongside the job's existing records of that type. A human decides to link the instance to one existing record or to create a new one; the default is always create.

`@azx/ribo-core` gains the instance-identity vocabulary: `ExistingRecord`, `InstanceLinkDecision`, and `LinkTargets`. `buildReviewRequest` accepts `existingRecords` per group; `resolveReview` carries link decisions through to the patch as `linkTargets` aligned with the positional array for each collection group. A missing link decision resolves to `null` (create), so a single matching existing record can never auto-link.

`@azx/ribo-adapter-snuggpro` provides `rankCandidates`, which orders existing records for a group using a tool-specific contradiction check: any captured identifying field that disagrees on both sides demotes the candidate. HVAC identifying fields are `hvacSystemEquipmentType`, `hvacHeatingSystemManufacturer`, `hvacHeatingSystemModel`, and `hvacHeatingSystemModelYear`.

`@azx/ribo-ui-react` exposes the decision in `useReview`: `existingRecords`, `rankedCandidatesOf`, `linkDecisionOf`, `linkInstance`, and `createInstance`. The link decision is submitted alongside leaf decisions and survives into the persisted `reviewOutcome`.
