# R1.5 — Field-Shape Contracts — Implementation Plan

> **For anyone implementing this, human or agent:** work task-by-task, in order. Each task ends with a
> commit and a green non-e2e gate. Steps use checkbox (`- [ ]`) syntax. If a task's premise turns out to
> be wrong against the actual code, **stop and say so** rather than improvising around it — that has
> already paid for itself repeatedly on this branch.

**Goal:** Separate the two field shapes `ToolAdapter<F, C>` conflates, move review onto flat dotted leaf
paths, and complete the write contract that separation reveals to be underspecified.

**Architecture:** The writable shape `V` is declared as a **patch** — every leaf optional, nullable
where a null is meaningful. The extraction schema is **derived** from it by stripping that optionality
and wrapping every leaf in the provenance envelope, so it stays strict and fully required. Review
addresses leaves by dotted path, carries each leaf's zod schema for rendering and validation, and
reassembles the nested patch on submit. `toWriteStep` parses the destination out of each item's own
`recording.ctx` and forwards the queue's idempotency key.

**Tech Stack:** TypeScript 6.0.3, **zod 4.4.3**, Vitest 4 (node `unit` + real-Chromium `browser`),
tsdown, pnpm 10.34.5 catalog.

**Design:** [`../design/r1.5-field-shape-contracts-design.md`](../design/r1.5-field-shape-contracts-design.md)
— **revision 2**. Read §1, §2 and §9 before Task 1; §9 lists what a first-draft version of this got
wrong, and every item there is now a requirement.

## How this plan is written

R2's plan specified exact code for everything, and on Phase A that produced three defects of one kind:
code written confidently into the plan about an external library's runtime behaviour, never executed.
So this plan states the **property to establish** and tells you to verify the API against the installed
version, giving literal code only for our own logic.

That is not licence to improvise the design — the linked design is settled, and revision 2 exists
because a review found four blocking defects in revision 1. It is an instruction to check the mechanism
before building on it, and to report what you found.

**One feasibility question is already answered**, so you do not have to rediscover it: zod 4.4.3's
`.shape`, `instanceof z.ZodObject` and `z.strictObject` are public and sufficient — no `._def` or
`._zod` access is needed — and the current Snugg Pro schema emits no `$ref`/`$defs`, so an exact
comparison in Task 1 is achievable. Verify rather than trust, but you are not walking into a wall.

## Global Constraints

- **Node >= 24, pnpm 10.34.5.** Every command from the repo root.
- **The gate for every task** (the `e2e` project is knowingly red on this branch — `extraction-ui` and
  `network-transition` poll for `done`, which R2 Phase A's review gate makes unreachable without a
  human, and R2 Task 18 owns them):
  ```bash
  pnpm typecheck && pnpm lint && pnpm format:check && pnpm build:packages \
    && pnpm check:resolve && pnpm build:app && pnpm check:pkg \
    && pnpm vitest run --project unit --project browser
  ```
  An **e2e** failure beyond those two named specs is new breakage — stop and report.
- **Every guard you add must be proven to discriminate.** Break the thing it guards, observe the
  failure, restore, and **report the observed output**. A test that passes either way advertises
  coverage that does not exist; four findings on this branch were exactly that, including one where the
  suggested assertion was itself vacuous. If a test cannot be made to fail, say so rather than leaving
  it in.
- **ESM-only.** `import type` for type-only imports (enforced by lint).
- **zod 4.4.3.** Verify introspection APIs against it, not zod-3 habits.
- `ribo-core` and `ribo-adapter-snuggpro` are **headless**: no `react`, no `document`, no `window`.
- **Dependencies point inward to `ribo-core`.** Core must never import an adapter — this constrains
  where the integration test lives (Task 5).
- **Public entry points only across packages**: `@azx/ribo-core`, never `@azx/ribo-core/src/...`.
- **Small, focused files.** Prefer a new file over growing one.
- **Never hand-format.** `pnpm format`. Prettier: 100 columns, double quotes, semicolons, trailing commas.
- **Do not touch the outbox schema.** R1.5 needs no migration (design §4). `reviewOutcomeSchema.fields`
  is `z.record(z.string(), z.unknown())`, which accepts nested values, and the touched-field lists are
  `z.array(z.string())`, which accepts dotted paths. Reaching for a version bump means the design has
  been misread.

## Task 1: Pin the JSON Schema, as a string, before changing anything

**Files:**

- Create: `packages/ribo-adapter-snuggpro/src/extraction-shape.test.ts`
- Create: a committed fixture holding the serialized JSON Schema (check for an existing fixture
  convention in the repo before inventing a location)

**Interfaces:** produces the safety net every later task is verified against.

**Why first.** R1.5 claims to change how the field set is described in TypeScript without changing what
the model is asked for. This snapshot is the evidence. Written before the refactor it proves something;
written after, it is a rubber stamp.

- [ ] **Step 1: Snapshot what is actually sent, not what you can regenerate**

Read `packages/ribo-extractor-openai/src/single-shot.ts` and note the exact `z.toJSONSchema` call and
its options, plus any post-processing before the result lands in `response_format.json_schema.schema`.
If there is post-processing, the fixture must include it or it pins the wrong artifact.

- [ ] **Step 2: Compare as a STRING, not with deep equality**

`openai-chat.ts` `JSON.stringify`s the whole request, so **key order is in the bytes on the wire**. Deep
equality would not see a reordering that changes what the model receives. Assert
`JSON.stringify(generated)` against the fixture's exact serialization.

Also assert the structural properties, so a different-but-equal schema is still caught: every object
closed (`additionalProperties: false`), every key in `required`, and no `minimum`/`maximum`/`pattern`
anywhere — OpenAI strict mode rejects those, which is why `confidence` is a bare `z.number()`.

Include a comment stating that **a mismatch means the derivation is wrong and the fixture must not be
regenerated to make the test pass.** That sentence is the fixture's entire value.

- [ ] **Step 3: Prove it discriminates, twice**

Two separate probes, because they catch different failures:

1. change one field's inner type in `SnuggFieldsSchema` → the test must fail;
2. **reorder two fields** in `SnuggFieldsSchema` without changing any of them → the test must fail. If
   it does not, the comparison is not actually order-sensitive and Step 2 is not done.

Restore, and report both observed outputs.

- [ ] **Step 4: Verify and commit**

## Task 2: `enveloped()` in core

**Files:**

- Create: `packages/ribo-core/src/enveloped.ts`, `enveloped.test.ts`
- Modify: `packages/ribo-core/src/index.ts`, `index.test.ts` (the barrel pins its exact export list)

**Interfaces:**

```ts
export const enveloped: <T extends z.ZodObject>(values: T) => z.ZodObject<Enveloped<T["shape"]>>;
export type Enveloped<V> = {
  readonly [K in keyof V]: V[K] extends object ? Enveloped<V[K]> : Extracted<V[K]>;
};
```

Additive — nothing consumes it until Task 3, so this task cannot break anything.

**The property**, per design §2.2 and §3: given a **patch** schema of plain values, produce the schema of
the same shape, **strict and fully required**, with every leaf wrapped by core's existing
`extractedSchema(inner)` (in `provenance.ts` — read it; `snuggpro` has a hand-rolled duplicate you delete
in Task 3).

**The subtle part, and the reason revision 1 was wrong.** A values leaf is `X.nullable().optional()`.
You must **strip both wrappers before applying `extractedSchema`**:

```
X.nullable().optional()  →  strip  →  X  →  extractedSchema(X)  →  { value: X.nullable(), … }
```

which reproduces today's `Extracted(X)` exactly, so Task 1's gate holds. Without the strip you get
`value: nullable(nullable(X))` and a nested `anyOf` — a silent change to what the model is asked for.

- [ ] **Step 1: Establish the introspection you need, and record it**

You need to: read an object's entries, unwrap optional/nullable wrappers, distinguish a nested object
from a leaf, and build a closed object from new entries. `.shape`, `instanceof z.ZodObject` and
`z.strictObject` are public in 4.4.3 and sufficient. Determine and **write down in your report**:

- how you unwrap `.optional()` / `.nullable()`, including a leaf wrapped in **both** and in either order;
- how you detect "nested object" explicitly, rather than via `try`/`catch`;
- whether rebuilding preserves strictness or you must re-apply it.

A throwaway scratch probe is a fine way to confirm. Do not commit it.

- [ ] **Step 2: Write the failing tests first**

- a flat patch of two leaves → both wrapped as `{ value: inner|null, confidence, sourceSpan }`;
- **stripping**: `X.nullable().optional()` and `X.optional().nullable()` both produce the same result as
  a bare `X` — and specifically **not** a doubly-nullable value. Assert on the generated JSON Schema
  here, not just the zod type, because the nested-`anyOf` failure is only visible there;
- a nested object → recursed, **not** wrapped as one envelope over the whole object. This is the defect
  R1.5 exists to prevent, so name the test for it;
- the output is **fully required and closed** even though the input was optional and open — parse must
  reject a missing key and an extra key;
- an unsupported shape throws **with the path in the message**: one case per kind you can construct
  (array, record, union of objects). If zod 4.4.3 makes one indistinguishable, say so rather than
  silently dropping it;
- **a type-level test** that `z.infer<ReturnType<typeof enveloped>>` retains the nested shape. A bare
  `z.ZodObject` return infers as a loose record and would silently stop type-checking all 34 fields —
  testing the standalone `Enveloped<V>` alias does **not** catch this.

- [ ] **Step 3: Implement; prove the throw path and the strip both discriminate**

Replace the throw with a fallback → unsupported-shape tests must fail. Remove the strip → the
doubly-nullable test must fail. Report both.

- [ ] **Step 4: Export, update the barrel test, verify, commit**

Check how `index.test.ts` treats type-only exports before adding `Enveloped` to the wrong list.

## Task 3: The contract switch

**Files:**

- Modify: `packages/ribo-core/src/adapter.ts` (`ToolAdapter`, `ToolAdapterExample`, `WriteMetadata`),
  `extractor.ts` (`ExtractionTarget`)
- Modify: `packages/ribo-adapter-snuggpro/src/` — `schema.ts` (the patch split; delete local
  `Extracted()`), `context.ts` (add `ctxSchema`), `adapter.ts`, `examples.ts`, `normalization.ts`,
  `instructions.ts` if it names the type, `index.ts`
- Modify: `packages/ribo-extractor-openai/src/single-shot.ts`
- Modify: the tests of all of the above

**Interfaces:**

- Consumes: `enveloped`, `Enveloped` (Task 2); Task 1's fixture as the gate.
- Produces: `ToolAdapter<V, C>` with `schema` (patch), `extractionSchema`, `ctxSchema`, and
  `write(fields, ctx, meta)`; `WriteMetadata`; `snuggValuesSchema`, `snuggExtractionSchema`,
  `SnuggValues`, `SnuggExtraction`, `snuggCtxSchema`. Tasks 4 and 5 build on all of it.

**Atomic and will not compile part-way.** Making `extractionSchema` required breaks `snuggProAdapter`
immediately; splitting the Snugg schema breaks the extractor. One commit is what keeps every checkpoint
meaningful. Expect a red tree until Step 6.

- [ ] **Step 1: `ToolAdapter`, `WriteMetadata`, `ctxSchema`**

Per design §2.3. Three additions and one signature change:

- `extractionSchema: ZodType<Enveloped<V>>`;
- `ctxSchema: ZodType<C>` — `Recording.ctx` comes back out of IndexedDB, so it crosses a trust boundary
  and needs a schema, not just a type parameter. `recordingSchema(jobContext)` already anticipates this
  shape;
- `WriteMetadata { idempotencyKey: string }`;
- `write: (fields: V, ctx: C, meta: WriteMetadata) => Promise<void>`.

`meta` is a third parameter rather than folded into `ctx` deliberately: `ctx` is _where to write_ and
comes from the recording; `meta` is _how to write safely_ and comes from the queue. Merging them would
let a host persist an idempotency key into a recording's context.

Keep the existing `@typeParam` reasoning about why `write` is a function property rather than a method
(contravariance; `adapter.test.ts` pins it with `@ts-expect-error`) — that is unchanged and must survive.
Add a paragraph on which schema is which and why one is derived.

- [ ] **Step 2: `ExtractionTarget`**

Currently `Pick<ToolAdapter<F, unknown>, "name" | "schema" | "instructions" | "examples">`. Pick
`extractionSchema` and carry that name across the boundary rather than renaming it to `schema` inside the
`Pick` — one name for one thing.

- [ ] **Step 3: `single-shot.ts`'s generics, which are more than one field name**

This is bigger than it looks. `SingleShotOptions.normalize`, `Extractor<F>` and `ExtractionResult<F>`
all currently speak `F`. Once the target exposes `ZodType<Enveloped<V>>`, those signatures would claim
the extractor returns plain `V` while it actually returns envelopes. Move all of them: `normalize`
consumes and returns `Enveloped<V>`, and `singleShotExtractor` returns `Extractor<Enveloped<V>>` with
its result type following.

- [ ] **Step 4: Split the Snugg Pro schema into a patch**

`SnuggFieldsSchema` becomes `snuggValuesSchema`, with each `Extracted(X)` unwrapped to
**`X.nullable().optional()`** — nullable because a null is a meaningful, written value (Snugg Pro's
`Not Tested`), optional because a rejected field must be absent from the patch. `healthSafety` becomes a
plain values object, itself `.optional()`. Then
`export const snuggExtractionSchema = enveloped(snuggValuesSchema);`.

Three things to get right:

- **Delete the local `Extracted()` helper.** It duplicates core's `extractedSchema`, and that duplication
  is how the shapes drifted apart unnoticed. Its doc comment carries real reasoning (independent
  nullability of `sourceSpan`; why `confidence` is a bare `z.number()`); core's version documents both at
  last reading — if anything is said better locally, move it rather than lose it.
- **Keep the field-level doc comments.** The 23 top-level fields carry Snugg Pro domain knowledge —
  hazard notes, the fuel axis-split, banding rules. They belong on the patch schema now. Losing them is
  the most expensive part of this task to redo.
- **`.strict()` on both objects.**

Name the types `SnuggValues` and `SnuggExtraction`. A temporary `SnuggFields` alias inside this commit is
acceptable if it makes the work tractable; delete it before you finish.

- [ ] **Step 5: `ctxSchema` for Snugg Pro, and re-type the rest**

`context.ts` defines `SnuggWriteContext`; add the zod schema it should have been inferred from, and have
the adapter declare it. If `SnuggWriteContext` is currently a hand-written interface, the schema becomes
the source of truth and the type is inferred off it — the pattern `recording.ts` documents ("because zod
is the source of truth, the generic lives on the schema factory and the type is inferred back off it").

`snuggExamples` types against `SnuggExtraction`; **its data must not change at all**, because it was
already envelope-shaped. Its header says it doubles as a fixture, so **if the data needs editing, the
derivation is wrong** — stop and investigate. Same for `normalizeFields`: types move, logic does not.

- [ ] **Step 6: Task 1's fixture must match, untouched**

```bash
pnpm vitest run packages/ribo-adapter-snuggpro
```

This is the moment the task is either right or wrong. If it fails, read the diff before changing
anything. Likely causes in order: the strip missing (look for a nested `anyOf`), strictness not
preserved, key order changed, a leaf detected as an object or vice versa. **Do not regenerate the
fixture.** If you conclude the fixture was wrong, that is a finding to report, not a thing to fix
quietly.

- [ ] **Step 7: Full gate, then commit as one change**

Record the _why_ in the message: four call sites need envelopes and two need values, and one type
parameter cannot be both.

## Task 4: Review addresses leaf paths, and validates

**Files:**

- Modify: `packages/ribo-core/src/review.ts`, `review.test.ts`, `contracts.test.ts`, `index.ts`,
  `index.test.ts`
- Check: `queue/outbox.ts`, `queue/relay.ts` (they name review types); `playground/src/ReviewPanel.tsx`
  (compilation only — rewritten in R2 Phase C)

**Interfaces:**

```ts
export type FieldPath = string;
export interface ReviewField {
  readonly extracted: Extracted<unknown>;
  readonly isGrounded: boolean;
  readonly schema: ZodType<unknown>; // this leaf's VALUE schema
}
export type ReviewFields = Readonly<Record<FieldPath, ReviewField>>;
export type FieldDecisions = Readonly<Record<FieldPath, FieldDecision>>;
export const buildReviewRequest: (
  extracted: Record<string, unknown>,
  transcript: Transcript,
  valuesSchema: z.ZodObject,
) => ReviewRequest;
```

**Two existing types change, stated so you do not have to guess:** `ReviewOutcome` **loses its type
parameter** — its `fields` is the reassembled nested `Record<string, unknown>`, and `toWriteStep`'s
`schema.parse` is what turns it into `V`; the three-branch union is otherwise unchanged.
`ReviewedValues<F>` is **deleted** — a top-level-key mapped type is the model being replaced. Check for
consumers first. If you think either should survive, report the reason rather than keeping it quietly.

**Four properties**, per design §2.4–§2.6 and §5:

1. **The schema enumerates the fields, not the data.** Walk `valuesSchema` for leaves; look each up in
   `extracted`. A leaf the model omitted is still presented, with the fully-specified sentinel
   `{ value: null, confidence: 0, sourceSpan: null }` — `confidence: 0` because `Extracted` requires a
   number and zero is honest.
2. **Each leaf carries its own value schema**, so a UI renders an editor with no adapter knowledge.
3. **Validation at submit.** Every accepted or edited value is parsed against its leaf schema, and a
   failure is an actionable per-path error. Without this the schema is decoration: a UI submitting
   `"thirty"` for a number would persist, advance to `writing`, and fail as a dead queue row long after
   the human who could fix it moved on.
4. **Completeness at runtime.** `Record` cannot express "a decision for every leaf" the way the old
   mapped type did, and `FieldDecisions` was non-`Partial` on purpose. Compare the submission's path set
   against the request's and reject a mismatch — missing **and** unexpected paths — rather than reading
   `undefined` and treating it as accepted.

- [ ] **Step 1: Write the failing tests first**

Use a small nested values schema of your own so assertions stay readable, but include a nested object of
at least two leaves. Cover: leaf enumeration including a nested `"group.leaf"`; a schema leaf absent from
`extracted` getting the exact sentinel; `isGrounded` true for a verbatim span and false for an invented
one; per-leaf `schema` parsing a valid value and rejecting an invalid one; validation rejecting an
edited value that fails its leaf schema, with the path named, and **not persisting**; completeness
rejecting a missing path and an unexpected path; reassembly producing `{ group: { leaf: v } }` not
`{ "group.leaf": v }`; a rejection **omitting** the key while `edited: null` **keeps** it as `null`; and
the two rules that must not regress — an edit equal to the extracted value still counts as `edited`, and
rejecting everything yields `edited` with no fields rather than `discarded`.

- [ ] **Step 2: Decide and record two things**

- **Path separator collisions.** A dotted path assumes no field name contains a `.`. Rejecting such a
  name loudly when walking the schema is almost certainly right for a bounded hand-written field set —
  but make it explicit, because the silent failure is a path addressing the wrong leaf.
- **Iteration order.** `resolveReview`'s `editedFields`/`rejectedFields` were previously stable because
  they followed the request's field order. Decide whether you rely on insertion order (and document it)
  or sort explicitly. Do not leave it undecided — 34 fields rendering in a different order each mount is
  an hour someone will lose.

- [ ] **Step 3: Implement, keeping the file's reasoning intact**

`review.ts`'s header was rewritten in R2 Phase A to describe review as a queue state, and its "Why this
is not `present(draft: T): Promise<T | null>`" section explains per-field granularity. Both are still
true and must survive with the leaf-path model folded in — the argument for per-field decisions is now
also an argument for per-**leaf** decisions.

- [ ] **Step 4: Confirm nested values round-trip the outbox with no schema change**

`submitReview` persists `reviewOutcome.fields` and `#write` passes it as `reviewed`. Design §4 says
nested values and dotted paths already fit `reviewOutcomeSchema`. **If that turns out false, stop** — it
means R1.5 needs a migration the design says it does not, which is a design question.

- [ ] **Step 5: Full gate, then commit**

## Task 5: `toWriteStep(adapter)`, and the real round trip

**Files:**

- Modify/create in `packages/ribo-core/src/` — `toWriteStep` beside `toExtractStep` or in its own small
  module; your call, say which and why. Plus `index.ts`, `index.test.ts`.
- Create: an integration test in **`packages/ribo-adapter-snuggpro`**, not in core (see Step 3).

**Interfaces:**

```ts
export function toWriteStep<V, C>(adapter: ToolAdapter<V, C>): WriteStep;
```

**It takes no `ctx`.** That is the correction revision 1 needed. For each item it parses
`input.item.recording.ctx` with `adapter.ctxSchema`, parses `input.reviewed` with `adapter.schema`, then
calls `adapter.write(fields, ctx, { idempotencyKey: input.idempotencyKey })`.

**Why per-item, not captured.** `Recording.ctx` exists so a host association "survives the round trip
through the queue". A composition capturing one `ctx` at construction would send two queued recordings
from two different jobs to whichever destination was captured — defeating the slot's entire purpose,
silently, in the direction that writes a basement's findings to the wrong house.

- [ ] **Step 1: Write the failing unit tests (core, synthetic adapter)**

- A valid patch and a valid ctx reach `write`, parsed.
- `idempotencyKey` reaches `write` in `meta`, and is **the same across a retry** of the same item.
- **Two items with different `recording.ctx` reach `write` with different contexts.** This is the
  regression guard for the captured-ctx bug; prove it fails against a version that resolves ctx once.
- A patch failing `adapter.schema` → `TerminalQueueError`, and `write` is **never called**.
- A `recording.ctx` failing `adapter.ctxSchema` → `TerminalQueueError`, `write` never called.
- Terminal rather than transient because both failures are deterministic; read `isTransientFailure` in
  `queue/backoff.ts` and confirm the classification is actually observed, not merely intended. Report
  what you found.

**Do not** assert that an all-rejected `reviewed: {}` reaches `toWriteStep` — R2 Phase A's relay guard
already rejects an empty outcome **before** any `WriteStep` runs, so such a test would prove nothing
about the real path. Exercise terminal classification with a non-empty but schema-invalid patch instead.

- [ ] **Step 2: Prove the ctx guard discriminates**

Temporarily change `toWriteStep` to resolve ctx once from the first item, and confirm the
two-different-contexts test fails. Restore and report.

- [ ] **Step 3: The round trip, on the real Snugg Pro field set**

**This test lives in `packages/ribo-adapter-snuggpro`, importing core through `@azx/ribo-core`.** Core
must never import an adapter — dependencies point inward only.

End to end in one test: `snuggValuesSchema` → `enveloped()` → **`snuggExamples[0].fields` as the model
response**, parsed by the extraction schema → `buildReviewRequest` → decisions covering every leaf,
including one edit inside `healthSafety` → `resolveReview` → `toWriteStep` → assert what reaches `write`.

Use the real fixture, **not a hand-built all-non-null object**. The fixture is full of honest nulls
(`coolingEquipmentType`, `ductLocation`, `ductSealing`, and more via its `env(null, null)` helper), and
that is precisely the path revision 1 of this design got wrong. `snuggProAdapter.write` throws by design
(write-back is gated on the Helix HMAC ask), so assert against a stub adapter sharing the real schemas;
say in your report which you used.

Assert specifically that **the edited nested leaf arrives in its nested position with the human's value,
not the model's**. That single assertion is R1.5 working.

- [ ] **Step 4: One rejected leaf must still write**

The test that proves patch semantics, and the one revision 1 would have failed. Reject exactly one of
the 34 leaves and assert the write **succeeds**, with that key **absent** from the patch and every other
key present. Then assert the neighbouring case: an accepted `null` arrives as a present `null`, distinct
from absent. Absent means "leave the host tool alone"; null means "write it as empty".

- [ ] **Step 5: Export, full gate, commit**

## Open questions carried out of implementation

1. **Typed leaf paths** (`Leaves<V>`, `AtPath<V, P>`) remain purely additive over this design. Revisit if
   path typos prove a real source of bugs in the field app.
2. **Grouping metadata for the UI.** Splitting the dotted path suffices today.
3. **Whether `normalize` belongs on the adapter** — it is typed against the extraction shape but passed
   separately to `singleShotExtractor`. R1.5 leaves the inconsistency; do not "fix" it here.
4. **Whether the patch schema should be derived too**, from a "full" schema alongside the extraction one.
   Not taken: the patch is what a host writes against, so it should be what a human reads.
