## 1. Goal

`ToolAdapter<F, C>` has one type parameter doing two jobs, and nothing noticed because **no code has
ever run the review-to-write path against a real adapter**. R1.5 separates the two shapes, fixes the
review contract the separation exposes, and completes the write contract that separation reveals to be
underspecified.

### 1.1 What `F` is actually used for

| Use site                                                                                | Needs         |
| --------------------------------------------------------------------------------------- | ------------- |
| `single-shot.ts`: `z.toJSONSchema(target.schema)` constraining the model's output       | **envelopes** |
| `single-shot.ts`: `target.schema.safeParse(raw)` — the trust boundary on the response   | **envelopes** |
| `single-shot.ts`: `JSON.stringify(example.fields)` as the **assistant** turn to imitate | **envelopes** |
| `normalize?: (fields: F) => F` — `normalizeFields` clamps `confidence` per envelope     | **envelopes** |
| `ToolAdapter.write: (fields: F, ctx: C) => Promise<void>`                               | **values**    |
| `review.ts`: `ExtractedFields<F>`, `ReviewedValues<F>`, `resolveReview`                 | **values**    |

`snuggpro`'s `SnuggFieldsSchema` resolves the conflict in favour of envelopes — every field is
`Extracted(...)` — which makes four of the six correct and two wrong. The envelope-shaped `F` is not a
passing mistake: the extractor genuinely depends on it. **So the fix is not to change which shape `F`
is. It is to name both.**

### 1.2 The nesting problem the separation exposes

`review.ts` maps over **top-level keys**:

```ts
export type ExtractedFields<F> = { readonly [K in keyof F]: Extracted<F[K]> };
```

`SnuggFieldsSchema` is 23 top-level fields **plus** `healthSafety`, itself an object of 11
`Extracted(HealthTestState)`. Against a values-shaped `V`, that produces
`healthSafety: Extracted<{ambientCo, venting, …}>` — one envelope for the whole matrix, when what
exists on the wire is one per test. An auditor could not accept the ambient-CO result while correcting
the asbestos one, which is the point of field-level review.

`playground/src/ReviewPanel.tsx` already walks this with a `flatten()` helper producing dotted paths.
That helper existing is the tell.

### 1.3 The write contract is underspecified, and R1.5 is what discovers it

Three gaps, all invisible until values actually flow to an adapter:

- **`write` cannot receive the idempotency key.** `WriteStepInput.idempotencyKey` is documented as "the
  only thing standing between an ambiguous success and a double-write", and `write(fields, ctx)` has
  nowhere to take it.
- **`write`'s destination cannot vary per recording.** `Recording.ctx` exists precisely so a host
  association "survives the round trip through the queue", with `recordingSchema(jobContext)` as the
  documented factory. Any write composition that captures a single `ctx` up front would send two
  recordings from two different jobs to whichever destination was captured first.
- **Nothing enforces `schema.parse` before a write.** R2 Phase A's review found this: `RelayOptions.write`
  is host-supplied, and the "adapter's schema is the trust boundary" reasoning described a boundary that
  was never installed anywhere.

### What R1.5 is not

- **Not a new adapter.** Snugg Pro remains the only one.
- **Not write-back.** `snuggProAdapter.write` still throws, gated on the Helix HMAC ask. R1.5 fixes the
  _contract_, not the egress.
- **Not the hook layer.** R2 Phase B owns `useReview`; this makes it possible to write correctly.
- **Not a prompt or extraction-quality change.** The JSON Schema the model receives must be
  **byte-identical**, and §7 makes that a gate.

## 2. Decisions

### 2.1 Two shapes: a declared patch, and a derived extraction schema

`V` is the writable shape and the source of truth. The extraction shape is **derived** from it.

**`V` is a patch, not a full record.** Every leaf is optional and nullable where a null is meaningful:

```ts
export const snuggValuesSchema = z.object({
  atticRValue: z.number().nullable().optional(),
  healthSafety: z.object({ ambientCo: HealthTestState.nullable().optional(), … }).optional(),
}).strict();
```

Patch rather than full replacement because that is what the product does. An auditor dictates one room;
that dictation must not blank fields a different dictation filled in. It is also forced by review:
`resolveReview` omits rejected fields, so a strict all-required schema would make **rejecting one leaf
of 34 a permanent write failure** — which would defeat field-level review entirely rather than merely
mishandling an edge case.

**Absent and null are different, and both are load-bearing:**

| Review outcome for a leaf          | In the patch              | Meaning at the write                         |
| ---------------------------------- | ------------------------- | -------------------------------------------- |
| `rejected`                         | key **absent**            | do not touch this field in the host tool     |
| `accepted` / `edited` with a value | key present, value set    | write it                                     |
| `accepted` / `edited` with `null`  | key present, value `null` | write it as empty — Snugg Pro's `Not Tested` |

That mapping is not invented here. `schema.ts` already documents it for the health matrix: a test the
auditor never mentions is `value: null`, an explicitly skipped one is `not_tested`, and "the
deterministic write layer renders BOTH as Snugg's `Not Tested` state". It is the same distinction
`review.ts` draws between `rejected` and `edited: null`, carried through to the wire.

### 2.2 `enveloped()` strips write-side optionality before wrapping

This is what makes byte-identity achievable and it is the subtlest decision here.

The extraction schema must stay **strict and fully required** — `provenance.ts`'s anti-hallucination
rule says the model must emit an explicit `null` rather than omit a key, because "an omitted key is
indistinguishable from a field the model never considered". So the patch's `.optional()` and
`.nullable()` must not survive into it:

```
values leaf   X.nullable().optional()
  strip    →  X
  wrap     →  extractedSchema(X)  ⇒  { value: X.nullable(), confidence, sourceSpan }
```

which is exactly today's `Extracted(X)`. Without the strip, `extractedSchema(X.nullable())` yields
`value: nullable(nullable(X))` and a nested `anyOf` in the JSON Schema — silently changing what the
model is asked for, and breaking §7's gate.

Nested objects strip `.optional()` and recurse. The derived extraction schema is therefore closed and
required at every level, while the patch it came from is open at every level. **The two schemas differ
in optionality by construction, and that is the design, not a leak.**

### 2.3 `ToolAdapter` carries both schemas, a context schema, and write metadata

```ts
export interface WriteMetadata {
  /** Send as `Idempotency-Key`. Stable across every retry of this item. */
  readonly idempotencyKey: string;
}

export interface ToolAdapter<V, C> {
  readonly name: string;
  /** The PATCH that gets written. Source of truth for `V`. */
  readonly schema: ZodType<V>;
  /** What the model must produce: `schema` stripped of optionality, every leaf enveloped. */
  readonly extractionSchema: ZodType<Enveloped<V>>;
  /** Parses `Recording.ctx` into the destination this adapter writes to. */
  readonly ctxSchema: ZodType<C>;
  readonly instructions: string;
  readonly examples?: readonly ToolAdapterExample<Enveloped<V>>[];
  write: (fields: V, ctx: C, meta: WriteMetadata) => Promise<void>;
}
```

`ctxSchema` is new and closes §1.3's second gap. `C` was already "a real type parameter, never
`unknown`" so the type system could check that a caller had what the adapter needed — but a _type_
cannot parse an `unknown` off a persisted row. `Recording.ctx` crosses a trust boundary (it comes back
out of IndexedDB), so it needs a schema, exactly as `recordingSchema(jobContext)` already anticipates.

`write` gains a third parameter rather than folding the key into `ctx`: `ctx` is _where to write_ and
comes from the recording, while `meta` is _how to write safely_ and comes from the queue. They have
different lifetimes and different sources, and merging them would let a host accidentally persist an
idempotency key into a recording's context.

### 2.4 Review addresses flat dotted leaf paths, with the schema as runtime authority

```ts
export type FieldPath = string; // "atticRValue", "healthSafety.ambientCo"

export interface ReviewField {
  readonly extracted: Extracted<unknown>;
  readonly isGrounded: boolean;
  /** This leaf's VALUE schema — for rendering an editor and validating an edit. */
  readonly schema: ZodType<unknown>;
}
export type ReviewFields = Readonly<Record<FieldPath, ReviewField>>;
export type FieldDecisions = Readonly<Record<FieldPath, FieldDecision>>;
```

Values are `unknown` here and the **zod schema is the runtime authority**. That is doc 04's stated
mechanism — "`ReviewCard` renders from the adapter's zod schema — a labeled, editable field per schema
key" — and it is the only thing available at runtime: a TypeScript type cannot tell a UI an enum's
members.

**Rejected: recursive mapped types.** Full leaf-level precision, but the UI must render recursively,
`resolveReview` must walk two trees in parallel, and a mismatch anywhere in a 24-field nested type
reports against the whole tree.

**Rejected: typed leaf paths via template literals** (`Leaves<V>`, `AtPath<V, P>`). It would catch a
path typo at compile time, but it sits _on top of_ the runtime mechanism rather than replacing it. Purely
additive later (§10).

### 2.5 Validation happens at review, not only at write

`ReviewField.schema` exists to be **used**, and R1.5 uses it. A submission is validated before it is
persisted: every accepted or edited value is parsed against its leaf schema, and a failure is returned
as an actionable per-path error.

Without this the schema is decoration. A UI submitting `"thirty"` for a number would persist, advance
the item to `writing`, and only then fail — surfacing as a dead queue row long after the human who
could fix it has moved on. Catching it at submit means the auditor is told which field is wrong while
they are still looking at it.

The adapter's `schema.parse` at write time stays as the outer boundary (§2.6). Two checks, deliberately:
per-leaf at review for a good error message, whole-patch at write because the write is what must not be
wrong.

### 2.6 Submission completeness is enforced at runtime

Moving from a mapped type to `Record<FieldPath, …>` loses a guarantee the old model had for free.
`FieldDecisions` was "not `Partial` on purpose", because a field with no decision is indistinguishable
from one the reviewer never saw. A string-keyed record accepts `{}`.

So `resolveReview` compares the submission's path set against the request's and rejects a mismatch —
missing paths _and_ unexpected ones — rather than reading `undefined` and treating it as accepted. The
type can no longer carry this; the runtime must.

### 2.7 `toWriteStep(adapter)` — the trust boundary, per item

```ts
export function toWriteStep<V, C>(adapter: ToolAdapter<V, C>): WriteStep;
```

Note it takes **no `ctx`**. For each item it:

1. parses `input.item.recording.ctx` with `adapter.ctxSchema` — the destination travels with the
   recording, so two queued recordings from two jobs write to two places;
2. parses `input.reviewed` with `adapter.schema` — this is where the §1.3 boundary finally exists;
3. calls `adapter.write(fields, ctx, { idempotencyKey: input.idempotencyKey })`.

Any parse failure is a `TerminalQueueError`: values or a context that fail their schema will fail
identically on retry, and spending eight backoff attempts on a deterministic failure only delays
telling a human.

## 3. `enveloped()`

**There are two type spaces here and they cannot be one type.** Revision 2 conflated them, and the
signature it published was not merely imprecise — it does not compile (`TS2344`: `z.ZodObject`'s first
parameter is constrained to a shape of `$ZodType`, and a value-space mapped type produces no such
thing). Both are needed:

```ts
/** SCHEMA space: mirrors the walk, so `enveloped()`'s return type preserves the shape. */
type EnvelopedShape<S extends z.core.$ZodLooseShape> = { … };

export const enveloped: <T extends z.ZodObject>(
  values: T,
) => z.ZodObject<EnvelopedShape<T["shape"]>, z.core.$strict>;

/** VALUE space: the inferred type of the derived schema. This is what `ToolAdapter` uses (§2.3). */
export type Enveloped<V> = {
  readonly [K in keyof V]-?: [NonNullable<V[K]>] extends [object]
    ? Enveloped<NonNullable<V[K]>>
    : Extracted<NonNullable<V[K]>>;
};
```

Three details in the value-space type are load-bearing, and each was a live defect before it was
written down:

- **`-?` strips optionality**, and it is §2.2 expressed at the type level. `[K in keyof V]` over a type
  parameter is _homomorphic_, so it preserves `?` from `V` — and `V` is a patch, so every key is
  optional. Without `-?` the exported type says the extraction shape may be missing keys, exactly
  inverting the property this section establishes, and it fails **silently**: `ZodType<Enveloped<V>>`
  still accepts the derived schema, and consumers simply get `fields.rValue` as possibly `undefined`.
- **`[NonNullable<V[K]>] extends [object]`**, tuple-wrapped, prevents distribution. A bare conditional
  spreads an enum leaf like `"passed" | "failed"` into a union of `Extracted<…>` branches.
- **The return type must preserve the shape.** A bare `z.ZodObject` infers as a loose record, so
  `z.infer<typeof snuggExtractionSchema>` would lose all 34 fields and silently stop checking anything.

`ExtractedFields<F>` in `review.ts` uses the homomorphic form without `-?` and is **correct there**,
because the `F` it maps is already envelope-shaped with no optional keys. The patch is what makes the
difference — do not copy that type into this one.

The walk, which must **throw rather than guess** on anything unlisted:

| Encountered                                                                       | Action                                  |
| --------------------------------------------------------------------------------- | --------------------------------------- |
| `.optional()` / `.nullable()`, either order (and `.nullish()`)                    | **unwrap and continue** (§2.2)          |
| `z.ZodObject` (nested)                                                            | recurse, producing a closed object      |
| enum, literal, string, number, boolean                                            | `extractedSchema(leaf)`                 |
| anything else (array, record, union — incl. discriminated, a `ZodUnion` subclass) | **throw**, naming the path and the kind |

**A known edge of that guard, recorded so it is not mistaken for a gap.** The table dispatches on
_kind_, so `z.number().min(0)` and `z.string().regex(…)` are an allowed `ZodNumber`/`ZodString`, pass,
and then emit the `minimum`/`pattern` keywords strict mode rejects. Constraining _inside_ an allowed
kind is indistinguishable from not doing so at this layer. It is caught downstream by the structural
half of §7's gate, which recursively forbids those keywords in the emitted JSON Schema — and that is
the right place for it: the check belongs where the artifact actually exists.

Throwing matters: the output becomes the JSON Schema sent in strict structured-output mode, and a
shape OpenAI rejects surfaces as an opaque API error far from its cause. The constraints being
preserved are documented in `provenance.ts` — every key required and nullable, closed objects, and no
numeric or string constraint keywords, which is why `confidence` is a bare `z.number()`.

## 4. `resolveReview`

Unchanged in purpose: still the one place "was this draft edited?" is decided, so every UI classifies
identically. What changes is that it walks dotted paths, validates, and rebuilds nesting.

- Reject a submission whose path set does not match the request's (§2.6).
- Validate each accepted/edited value against its leaf schema (§2.5).
- `accepted` / `edited` paths set their value at that path in a fresh nested object.
- `rejected` paths are **omitted** — which is now well-defined, because `V` is a patch (§2.1).
- `editedFields` / `rejectedFields` carry dotted paths.

**`ReviewOutcome` loses its type parameter.** Its `fields` is the reassembled nested
`Record<string, unknown>`; the adapter's `schema.parse` in `toWriteStep` is what turns it into `V`. The
three-branch union and its fields are otherwise unchanged. **`ReviewedValues<F>` is deleted** — it was
a top-level-key mapped type, which is the model being replaced.

The two rules that are choices, kept verbatim: an edit whose value equals the extracted one still
counts as `edited` (the signal is what the human _touched_), and rejecting every field yields `edited`
with no fields rather than `discarded` (a statement about the extraction, not the recording). Note the
relay already refuses to write an empty field set, so the all-rejected case terminates at the relay
guard, not in the adapter.

**No outbox migration.** `reviewOutcomeSchema.fields` is `z.record(z.string(), z.unknown())`, which
accepts a nested object, and the touched-field lists are `z.array(z.string())`, which accepts dotted
paths. Worth stating because a reader would reasonably expect a v2.

## 5. The sentinel for an omitted leaf

`buildReviewRequest` walks the **values schema** to decide which leaves exist (so a leaf the model
omitted is still presented rather than vanishing), and a missing leaf gets a fully-specified envelope:

```ts
{ value: null, confidence: 0, sourceSpan: null }
```

`confidence: 0` rather than omitted, because `Extracted` requires a number. Zero is the honest value:
nothing was extracted, so there is nothing to be confident about. `isGrounded` is `false`, since a
`null` span cannot be a verbatim quote.

## 7. Testing

The load-bearing gate is a **characterisation test written first**:

- **The JSON Schema must be identical, compared as a string.** Snapshot what `single-shot.ts` actually
  sends today, then assert the derived schema serializes identically. **String comparison, not deep
  equality** — key order is in the request bytes, because the transport `JSON.stringify`s the request,
  and deep equality would not see a reordering. If it does not match, the derivation is wrong; do not
  regenerate the fixture.
- `enveloped()`: leaves wrapped, nested objects recursed, `.optional()`/`.nullable()` stripped, output
  closed and fully required, a throw naming the path for each unsupported shape, and a **type-level**
  test that `z.infer` of the result retains the nested shape.
- **The round trip on the real Snugg Pro field set**, using `snuggExamples[0].fields` as the model
  response rather than a hand-built all-non-null object — the fixture is full of honest nulls, which is
  exactly the path revision 1 got wrong. Values → enveloped → parse → `buildReviewRequest` → decisions
  including one edit inside `healthSafety` → `resolveReview` → `toWriteStep` → assert what reaches
  `write`.
- **One rejected leaf must still write.** Reject exactly one of the 34, and assert the write succeeds
  with that key **absent** and every other key present. This is the test that proves patch semantics
  work; revision 1 would have failed it.
- An accepted `null` reaches `write` as a present `null`, distinct from the rejected case above.
- Submission validation: an edited value failing its leaf schema is rejected at submit with the path
  named, and never persisted.
- Submission completeness: a missing path and an unexpected path are both rejected.
- `toWriteStep`: `idempotencyKey` reaches `write` and is stable across a retry; two items with different
  `recording.ctx` write to different destinations; a bad ctx and a bad patch are both terminal.

Every guard must be shown to fail with the thing it guards removed.

## 9. What changed in revision 2

Review of revision 1 found four blocking defects, all in the write path — unsurprising in hindsight,
because R1.5 is the first work to exercise review-to-write end to end:

1. **Values leaves must be nullable, and `enveloped()` must strip that before wrapping.** Revision 1
   unwrapped `Extracted(X)` to a bare `X`, which would have made every honest `null` a terminal parse
   failure. `snuggExamples` is full of them.
2. **`V` is a patch.** Revision 1 kept every key required while `resolveReview` omitted rejected keys,
   so rejecting one leaf of 34 could never parse. §2.1 now defines absent-vs-null semantics.
3. **`write` needs the idempotency key** (§2.3). Revision 1 left it stranded on `WriteStepInput`.
4. **`toWriteStep` must derive `ctx` per item** (§2.7). Revision 1 captured one `ctx` at construction,
   which would have written recordings from different jobs to a single destination and defeated
   `Recording.ctx`'s stated purpose.

Also corrected: `ReviewField.schema` is now actually enforced (§2.5); submission completeness is
checked at runtime (§2.6); `enveloped()`'s return type preserves the shape (§3); the JSON Schema gate
compares strings not deep equality (§7); and the sentinel envelope is fully specified (§5).

### 9.1 What changed in revision 3

Found while implementing §3. Revision 2 published

```ts
export const enveloped: <T extends z.ZodObject>(values: T) => z.ZodObject<Enveloped<T["shape"]>>;
```

which **does not compile**: it applies a value-space mapped type to `T["shape"]`, and `z.ZodObject`'s
parameter is constrained to a shape of `$ZodType` (`TS2344`, missing `_zod` and `~standard`). In schema
space the conditional also discriminates nothing, since every zod instance satisfies
`V[K] extends object`. §3 now names both spaces and says why one type cannot serve them.

The same section gained the `-?` modifier and the tuple-wrapped conditional. Both were live defects in
the implementation before being written down — without `-?`, every key of the extraction type is
optional, silently inverting §2.2.

## 10. Open questions

1. **Typed leaf paths** remain available as a purely additive change. Revisit if path typos prove a real
   source of bugs in the field app.
2. **Grouping metadata for the UI.** Splitting the dotted path is enough today. If a second adapter needs
   ordering the path does not imply, that belongs on the adapter.
3. **Does `normalize` belong on the adapter?** It is typed against the extraction shape but passed
   separately to `singleShotExtractor`. R1.5 leaves the inconsistency; naming it so it is not mistaken
   for something this design settled.
4. **Should the patch schema be derived too?** `V` is hand-written as a patch while the extraction schema
   is derived from it. One could instead declare a "full" schema and derive both. Not taken: the patch is
   the thing a host writes against, so it should be the thing a human reads.
