## 1. Goal

`ToolAdapter<F, C>` has one type parameter doing two jobs, and nothing noticed because no code ever
ran review against a real adapter. R1.5 separates them, and fixes the review contract that the
separation exposes.

### 1.1 What `F` is actually used for

| Use site                                                                                        | Needs         |
| ----------------------------------------------------------------------------------------------- | ------------- |
| `single-shot.ts`: `z.toJSONSchema(target.schema)` constraining the model's output               | **envelopes** |
| `single-shot.ts`: `target.schema.safeParse(raw)` — the trust boundary on the response           | **envelopes** |
| `single-shot.ts`: `JSON.stringify(example.fields)` as the **assistant** turn to imitate         | **envelopes** |
| `ToolAdapter.normalize?: (fields: F) => F` — `normalizeFields` clamps `confidence` per envelope | **envelopes** |
| `ToolAdapter.write: (fields: F, ctx: C) => Promise<void>`                                       | **values**    |
| `review.ts`: `ExtractedFields<F>`, `ReviewedValues<F>`, `resolveReview`                         | **values**    |

`snuggpro`'s `SnuggFieldsSchema` resolves the conflict in favour of envelopes — every field is
`Extracted(...)` — which makes four of the six correct and two of them wrong. `write` claims to take
values and is handed envelopes; `review.ts` claims `F` is values and would double-envelope it. The
envelope-shaped `F` is not a mistake someone made in passing: the extractor genuinely depends on it.

**So the fix is not to change which shape `F` is. It is to name both shapes.**

### 1.2 The nesting problem the separation exposes

`review.ts` maps over **top-level keys**:

```ts
export type ExtractedFields<F> = { readonly [K in keyof F]: Extracted<F[K]> };
```

`SnuggFieldsSchema` is 23 top-level fields **plus** `healthSafety`, itself an object of 11
`Extracted(HealthTestState)`. Against a values-shaped `V`, the mapped type produces
`healthSafety: Extracted<{ambientCo, venting, …}>` — **one envelope for the whole matrix**, when what
exists on the wire is one envelope per test. An auditor could not accept the ambient-CO result while
correcting the asbestos one, which is the entire point of field-level review.

`playground/src/ReviewPanel.tsx` already walks this structure with a `flatten()` helper producing
dotted `path` strings. That helper existing is the tell: top-level-key review was never going to be
enough for the only adapter that exists.

### What R1.5 is not

- **Not a new adapter.** Snugg Pro remains the only one.
- **Not write-back.** `writing` still terminates at the stub, gated on the Helix HMAC ask.
- **Not the hook layer.** R2 Phase B owns `useReview`; this makes it possible to write correctly.
- **Not a prompt or extraction-quality change.** The JSON Schema the model receives must be
  **byte-identical** before and after, and §6 makes that a gate. R1.5 is a refactor of how that
  schema is _described in TypeScript_, not of what the model is asked for.

## 2. Decisions

### 2.1 Two named shapes, one declared and one derived

`V` is the writable values shape and is the source of truth. The extraction shape is **derived** from
it by wrapping every leaf in the provenance envelope:

```ts
export const snuggValuesSchema = z.object({ … }).strict();          // declared
export const snuggExtractionSchema = enveloped(snuggValuesSchema);  // derived
export type SnuggValues = z.infer<typeof snuggValuesSchema>;
export type SnuggExtraction = z.infer<typeof snuggExtractionSchema>;
```

Derived rather than declared twice, because two hand-written schemas for one field set is a drift
surface with no compensating benefit — and the drift would be silent in the direction that matters:
an extraction schema carrying a field the write schema lacks means the model is asked for something
that can never be written.

`enveloped()` lives in `@azx/ribo-core` and builds on `extractedSchema(inner)`, which already exists
in `provenance.ts`. Note that `snuggpro` currently carries a **hand-rolled duplicate** of
`extractedSchema` called `Extracted()`; R1.5 deletes it. That duplication is how the two shapes drifted
apart unnoticed in the first place.

### 2.2 `ToolAdapter` carries both schemas

```ts
export interface ToolAdapter<V, C> {
  readonly name: string;
  /** Parses the values that get WRITTEN. The source of truth for `V`. */
  readonly schema: ZodType<V>;
  /** What the model must produce: `schema` with every leaf enveloped. Derive with `enveloped()`. */
  readonly extractionSchema: ZodType<Enveloped<V>>;
  readonly instructions: string;
  /** Few-shot examples, in the EXTRACTION shape — they are the assistant turns the model imitates. */
  readonly examples?: readonly ToolAdapterExample<Enveloped<V>>[];
  /** Writes reviewed values into the host tool. Rejects if the write fails. */
  write: (fields: V, ctx: C) => Promise<void>;
}
```

`write`'s signature does not change. It was always `(fields: V, ctx: C)`; it just finally _means_
values — which is what `resolveReview` produces and what the relay already passes as
`WriteStepInput.reviewed` after R2 Phase A.

`ExtractionTarget` picks `extractionSchema` instead of `schema`, so `single-shot.ts` changes in one
field name. `normalize` types against `Enveloped<V>`.

### 2.3 Review addresses flat dotted leaf paths, and the schema is consulted at runtime

```ts
/** A dotted path to one reviewable leaf: "atticRValue", "healthSafety.ambientCo". */
export type FieldPath = string;

export interface ReviewField {
  readonly extracted: Extracted<unknown>;
  readonly isGrounded: boolean;
  /** The zod schema for THIS leaf's value — for rendering an editor and validating an edit. */
  readonly schema: ZodType<unknown>;
}

export type ReviewFields = Readonly<Record<FieldPath, ReviewField>>;
export type FieldDecisions = Readonly<Record<FieldPath, FieldDecision>>;
```

Values are `unknown` at this boundary and the **zod schema is the runtime authority**. That is not a
concession — it is the mechanism doc 04 specified from the start: "`ReviewCard` renders from the
adapter's zod schema — a labeled, editable field per schema key." A UI needs the enum's members to
draw a select and the number's type to draw a number input, and neither is available from a
TypeScript type at runtime. Carrying the per-leaf schema on `ReviewField` is what makes a
schema-driven review card possible with no adapter knowledge in the UI.

**Rejected: recursive mapped types** (`Enveloped<V>`, `ReviewFields<V>` mirroring `V`'s shape). Full
leaf-level type precision, but the UI must render recursively, `resolveReview` must walk two trees in
parallel, and a mismatch anywhere in a 24-field nested type reports against the whole tree — the
error messages are the cost that gets paid every day.

**Rejected: typed leaf paths via template literals** (`Leaves<V>`, `AtPath<V, P>`). It would make
`edit("healthSafety.ambientC", …)` a compile error, which is genuinely nice. But it sits _on top of_
the runtime-schema mechanism rather than replacing it — the UI still needs the schema to render — so
it buys a typo check for a large amount of type machinery that is slow to check and hard to debug.
Recorded as a possible later addition (§8), because it is purely additive over this design.

### 2.4 The schema enumerates the fields, not the extracted data

`buildReviewRequest` walks the **values schema** to decide which leaves exist, and looks each one up
in the extracted data:

```ts
export const buildReviewRequest = (
  extracted: Record<string, unknown>,   // the persisted envelope map, still nested
  transcript: Transcript,
  valuesSchema: z.ZodObject,            // NEW: the authority on what fields exist
): ReviewRequest
```

Driving from the schema rather than the data means a field the model silently omitted is still shown
to the auditor — as an envelope with a `null` value and no span — rather than vanishing from the
review card. `provenance.ts`'s anti-hallucination rule already requires the model to emit every key,
so this is defence in depth against the one failure mode that rule cannot catch: a response that
parsed under an older schema version.

### 2.5 `toWriteStep(adapter, ctx)` — the trust boundary becomes real

R2 Phase A's review found that `RelayOptions.write` is host-supplied, so nothing in `ribo-core`
enforces `adapter.schema.parse` before a write. The design reasoning at the time leaned on "the
adapter's `schema.parse` is the trust boundary", and that boundary was not actually installed
anywhere.

R1.5 adds the missing composition, mirroring the `toExtractStep(extractor)` that already exists:

```ts
/**
 * Collapse a `ToolAdapter` onto the relay's injected `WriteStep`.
 *
 * THIS is where `schema.parse` runs. The relay hands over `reviewed` — the flat
 * values review settled on — and this parses them into `V` before calling
 * `adapter.write`. A host wiring `write:` by hand skips the boundary, which is
 * exactly what happened before this existed.
 */
export function toWriteStep<V, C>(adapter: ToolAdapter<V, C>, ctx: C): WriteStep;
```

A parse failure is a `TerminalQueueError`: values that do not satisfy the adapter's schema will not
satisfy it on a retry either, and burning eight backoff attempts on a deterministic failure only
delays telling a human.

## 3. `enveloped()`

```ts
/** Wrap every leaf of a values schema in the provenance envelope. */
export const enveloped = <T extends z.ZodObject>(values: T): z.ZodObject;
export type Enveloped<V> = { readonly [K in keyof V]: V[K] extends object ? Enveloped<V[K]> : Extracted<V[K]> };
```

The walk rule, and it must **throw rather than guess** on anything unlisted:

| Encountered                                               | Action                          |
| --------------------------------------------------------- | ------------------------------- |
| `z.ZodObject` (nested)                                    | recurse, preserving `.strict()` |
| enum, literal, string, number, boolean                    | `extractedSchema(leaf)`         |
| anything else (array, union of objects, record, optional) | **throw**, naming the path      |

Throwing matters more than it looks. The output of this function becomes the JSON Schema handed to
the model in strict structured-output mode, and a shape OpenAI rejects surfaces as an opaque API
error a long way from its cause. `provenance.ts` already documents the constraints this preserves:
every key required and nullable (never `.optional()`, so "not mentioned" must be an explicit `null`),
closed objects, and no numeric or string constraint keywords — which is why `confidence` is a bare
`z.number()` rather than `.min(0).max(1)`.

## 4. `resolveReview` reassembles the nested shape

Unchanged in purpose: it is still the one place "was this draft edited?" is decided, so every UI
classifies identically. What changes is that it walks dotted paths and rebuilds nesting.

```ts
export const resolveReview = (
  request: ReviewRequest,
  submission: ReviewSubmission,
): ReviewOutcome;
```

- `accepted` / `edited` paths set their value at that path in a fresh nested object.
- `rejected` paths are **omitted** — absent, not `null`. The `rejected` vs `edited: null` distinction
  survives verbatim: rejecting drops the field, editing to `null` asserts there is nothing to record.
- `editedFields` and `rejectedFields` are arrays of dotted paths.

**Phase A's persisted schema already accommodates this with no change.** `reviewOutcomeSchema.fields`
is `z.record(z.string(), z.unknown())`, and an `unknown` value accepts a nested object;
`editedFields` / `rejectedFields` are already `z.array(z.string())`, and a dotted path is a string.
So there is no second outbox migration in R1.5 — worth stating, because a reader would reasonably
expect one.

The two rules from the current implementation are kept and still deserve their comments: an edit whose
value equals the extracted one still counts as `edited` (the signal is what the human _touched_), and
rejecting every field yields `edited` with no fields rather than `discarded` (a statement about the
extraction, not the recording).

## 6. Testing

The load-bearing gate is a **characterisation test**, written first, before any refactor:

- **The JSON Schema must be byte-identical.** Snapshot `z.toJSONSchema(SnuggFieldsSchema, { target: "draft-2020-12" })`
  against today's code, then assert `z.toJSONSchema(snuggExtractionSchema, …)` equals it after the
  split. This is the whole safety net: it proves the model is asked for exactly what it was asked for
  before, so extraction quality cannot silently move. If it does not match, the derivation is wrong —
  do not update the snapshot to make it pass.
- `enveloped()` unit tests: flat leaves wrapped, nested objects recursed, `.strict()` preserved, every
  key required and nullable, and a throw with the offending path for each unsupported shape.
- `examples.ts` continues to type-check against the extraction shape, which the file header already
  says makes it double as a fixture — so a bad derivation breaks it.
- `review.test.ts`: path enumeration from the schema (including a leaf the extracted data omits),
  grounding per leaf, reassembly of nested values, `rejected` omitted vs `edited: null` present, and
  dotted paths in `editedFields` / `rejectedFields`.
- `toWriteStep`: a schema-satisfying outcome reaches `adapter.write`; a failing one raises
  `TerminalQueueError` and never calls `write`.
- Round trip, as one test: `snuggValuesSchema` → `enveloped` → a model-shaped response →
  `buildReviewRequest` → decisions → `resolveReview` → `adapter.schema.parse`. That is the whole
  contract, and it is the test that would have caught the original defect.

`./check.sh` green, per AGENTS.md §7.

## 7. Docs this falsifies

- **Doc 03's `ToolAdapter` row** describes one schema.
- **Doc 04's schema-driven `ReviewCard`** is right in mechanism but says "a labeled, editable field
  per schema **key**" — it is per **leaf path**, which for Snugg Pro is 34 rather than 24.
- **AGENTS.md §4's "adapters are the only place tool-specific knowledge lives"** stays true and gets
  stronger: the UI now needs no adapter import at all, only the schema on `ReviewField`.
- **`review.ts`'s header**, rewritten in R2 Phase A, describes per-field decisions over `F`'s keys. It
  needs the leaf-path model folded in.

## 8. Open questions

1. **Typed leaf paths** (§2.3's second rejected option) remain available as a purely additive later
   change: `Leaves<V>` and `AtPath<V, P>` over the same runtime structure. Worth revisiting if path
   typos turn out to be a real source of bugs in the field app; not worth the type machinery on
   speculation.
2. **Grouping metadata for the UI.** A reviewer wants Snugg Pro's 11 health-safety tests under one
   heading. Today a UI can split the dotted path itself, which is enough. If a second adapter wants
   ordering or grouping that the path does not imply, that belongs on the adapter — not derived.
3. **Does `normalize` belong on the adapter at all?** It is typed against the extraction shape and is
   passed separately to `singleShotExtractor` today rather than read off the adapter. R1.5 leaves that
   inconsistency alone; naming it here so it is not mistaken for something this design settled.
