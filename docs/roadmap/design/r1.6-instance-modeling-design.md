## 1. Goal

**A house with two HVAC systems cannot currently be represented, and the schema will happily record a
sentence about one machine as a fact about the other.**

Snugg Pro models `hvac`, `attic`, `wall`, `window` and `dhw` as per-instance child resources — each
its own record with its own uuid, created by `POST /jobs/{jobId}/<type>` and updated by `POST
/jobs/<type>/{uuid}`. Our `snuggValuesSchema` models exactly one of each. Only `basedata` and
`health` are genuine singletons in the API, and only those two are correctly modeled today.

R1.6 makes the five per-instance groups collections, end to end: schema, extraction, review, write.

## 2. The evidence, and why it is not hypothetical

The re-annotated corpus (`spikes/extraction-snuggpro/`, 13 transcripts double-annotated) hit this on
**three of thirteen transcripts** — 05, 08 and 12. Two of the three are unrepresentable.

Transcript 08 is the clearest. The auditor describes:

> "heating is a furnace, forced air, I can see the supply plenum coming off it… It's a **Lennox**,
> model G-something"
>
> "**The AC's got its own ducts** up in the attic, standalone, **separate from anything the furnace
> does**… the ducts up here have no insulation on them at all, bare metal… I'd call the sealing
> **very leaky**"

The identity fields describe the furnace. The duct fields describe the AC. The auditor states
outright that they are separate systems. `HvacFields` has one slot for each.

- Set `hvacSystemEquipmentType` to the furnace, and the record claims the furnace's ducts are
  uninsulated and very leaky. They are the AC's ducts. The furnace's ducts were never described.
- Set it to the AC, and `hvacHeatingSystemManufacturer` — a field with "Heating" in its name — holds
  the furnace's brand.

**Either way the record asserts something false about a real appliance**, and this is why it matters
more than missing data: every individual field is plausible. Lennox is a real manufacturer. "Very
leaky" is a real duct condition. A reviewer scanning the card sees nothing wrong, because nothing
_is_ wrong field by field. Only the combination is a lie, and field-level review is structurally
blind to it.

Transcript 12 is the merciful variant: two systems, but the auditor says _"Do not log the old
boiler."_ One system is explicitly out of scope, so a human can comply and the result is honest.
That case needs no schema change — it needs the schema to have somewhere to put the second system so
the exclusion is a choice rather than a forced loss.

Both annotators on 05 and 08 found the collision independently, both picked the same instance, and
both **deliberately declined** to mark it with the `symmetric` mechanism — correctly, since that
mechanism resolves one enum's conflated axis on a single entity, not two entities competing for one
slot. One noted it deserves its own handling. This design is that handling.

## 3. Scope

| Group      | API shape                       | Change         |
| ---------- | ------------------------------- | -------------- |
| `basedata` | singleton (`POST .../basedata`) | none           |
| `health`   | singleton (`POST .../health`)   | none           |
| `hvac`     | per-instance child resource     | **collection** |
| `attic`    | per-instance child resource     | **collection** |
| `wall`     | per-instance child resource     | **collection** |
| `window`   | per-instance child resource     | **collection** |
| `dhw`      | per-instance child resource     | **collection** |

The corpus surfaced HVAC first because that is what auditors talk about most. The gap is identical
for wall assemblies and window groups, which real houses have several of, and the API models the same

## 4. Three constraints this runs into

### 4.1 Leaf paths currently forbid array indices, on purpose

`field-path.ts`'s `childPath` **throws** on an integer-like key:

> An integer-like key breaks the documented iteration order. `review.ts` states that fields are
> presented in schema-declaration order […]; that holds because JavaScript preserves insertion order
> for string keys — _except_ array-index-like ones, which are hoisted to the front in numeric order.
> One such key would reorder a 34-field review card with no error.

So `hvac.0.hvacDuctLeakage` is not merely unsupported, it is explicitly rejected with an error
explaining why. This is a guard doing its job, and the fix is to give arrays a distinguishable
syntax rather than to weaken it.

**Decision:** leaf paths gain a bracketed index segment — `hvac[0].hvacDuctLeakage`.

> **REFINED by §10.2.** The bracket stays and so does everything this section asks for, but it
> carries a **stable key** rather than an ordinal — `hvac[k3].hvacDuctLeakage`. That removes the
> renumbering hazard of revision 4's item 5, and it also dissolves this section's own opening problem
> at the root, since a non-integer-like key cannot be hoisted in property order.

**Revision 3 justified this with a false claim and it is corrected here.** It said a bracket is
unambiguous "because `childPath` already refuses `.` and `[` is not a legal character in the wire
property names the schema uses." `childPath` refuses `.` and integer-like keys — **it does not
refuse `[`** (verified: `field-path.ts:92,99`). And `FieldPath` is a _core_ contract, not a
Snugg-only one, so what Snugg's wire names happen to contain is not the governing fact: another
adapter may legally declare an object key `hvac[0]`, which would collide with array element zero.

So this needs two things revision 3 did not ask for:

- **A reserved-character rule.** `childPath` must reject (or escape) `[` in an object key, the same
  way it already rejects `.`, and for the same reason — a key that can impersonate a path segment
  makes the path address the wrong thing.
- **One shared path grammar, used for construction _and_ reassembly.** Emitting the syntax is half
  the change. `resolveReview` reassembles with `path.split(".")` (`review.ts:487`), so
  `hvac[0].hvacDuctLeakage` would rebuild as `{ "hvac[0]": { … } }` — an object whose key is the
  literal text — rather than `{ hvac: [{ … }] }`. Construction and parsing must share one
  implementation with distinct object-key and array-index segment types, or they will disagree.

### 4.2 Arrays break "the schema enumerates the leaves, not the data"

This is the load-bearing one. `buildReviewRequest` walks the **values schema** and looks each leaf up
in the extracted data, never the reverse. `review.ts` states why:

> Enumerating the data instead would make an omitted field vanish from the review card, which is
> indistinguishable to the auditor from a field that was extracted correctly and is exactly the
> silence the provenance envelope exists to forbid.

A schema cannot say how many systems a transcript described. So the invariant has to be restated
rather than abandoned:

> **The data determines how many instances exist. The schema determines every leaf within each
> instance.**

That preserves the property that actually matters — no leaf of a present instance can silently
vanish — while accepting that instance _count_ is necessarily data-driven.

**The regression this introduces, and its fix.** Under the flat schema, a transcript that mentioned
no HVAC still produced twelve reviewable null leaves, so an auditor could notice "you missed the
furnace" and fill it in. Under collections, `hvac: []` produces no rows at all, and there is nothing
to correct. That is a real loss of reviewability.

> **SUPERSEDED by §10.1.** The placeholder proposed in the next paragraph is **not built**. It
> collapses the patch semantics (revision 4, item 4) and the fix is to delete it rather than specify
> it: an empty collection stays empty, and reviewability is supplied by a group-level affordance
> instead of a manufactured row. The paragraph is retained because §10.1 argues against it and a
> reader needs to see what was rejected.

Strict structured-output mode rejects `minItems` (the same constraint-keyword family as
`minimum`/`maximum`, per `provenance.ts`), so we cannot require ≥1 in the schema. Instead:
**`normalizeFields` inserts one all-null instance into any empty collection** before review. That is
exactly what the deterministic post-model pass exists for, it keeps "every leaf always appears" true
of the first instance of every group, and it is model-free.

`resolveReview` must then treat an instance whose every leaf was rejected as **absent from the
patch**, not as an instance of nothing — otherwise reviewing a house with no water heater would
`POST` an empty `dhw` record.

### 4.3 Extraction must now segment, which is a new hallucination surface

Today the model fills a fixed form. With collections it must first decide _how many_ systems a
transcript describes, and only then fill them. That is a harder task, and it introduces a failure
mode that does not exist today: **inventing a second system** where the auditor described one.

The corpus gives us the shape of the hazard. Transcript 08's auditor self-corrects mid-sentence —
_"up in the attic there's an air handler, no wait, the furnace itself is in the closet and the AC air
handler's the separate thing"_ — which is exactly the kind of passage that could be read as one
system or two. Transcript 10 has a **decoy**: a neighbour's oil boiler, mentioned and immediately
disclaimed, which both annotators correctly excluded and which an eager segmenter would happily
promote to a second instance.

Two mitigations, both cheap:

- **Extraction instructions gain a segmentation rule** — but _not_ the one revision 3 proposed.
  "A separate physical unit" is the wrong criterion: a furnace, a condenser and an air handler are
  three physical units and **one** shared-duct Snugg HVAC record. The rule has to be framed in terms
  of what the vendor models as one record, not what stands on the floor as one box. It must also
  cover a mention followed by an exclusion ("ignore that, that's the neighbour's" — transcript 10's
  decoy), and it does not transfer unchanged to `attic`/`wall`/`window`, whose instances are
  assemblies and groups rather than appliances.

  Revision 3 emphasised **over**-segmentation. The corpus's actual failure is the opposite and worse:
  under-segmentation, and correct-count-wrong-attribution. Other distinct failures a single rule will
  not catch: merging two systems that share a location, fuel or ducts; duplicating one system after
  a self-correction; and treating decommissioned, proposed or replacement equipment as current.

- **The scorer gains per-instance field _attribution_, not just a count.** Revision 3 proposed an
  instance-count measure. **That measure passes the exact defect R1.6 exists to fix**: a run can emit
  the correct number of instances and still put the furnace's identity and the AC's ducts in the same
  element, which is precisely transcript 08's collision. Count is worth having as one metric, but the
  load-bearing one is whether each field landed on the right instance — and it must be
  permutation-insensitive, or a run that emits the same two systems in the other order is penalised
  while genuine cross-instance mixing goes unnoticed.

  **The corpus cannot score that yet.** Its leaf records are single-instance by construction, and the
  multi-system transcripts encode their collisions in prose `notes` because that is all the current
  format could express — transcript 08 deliberately stores furnace and AC facts in one `hvac.*`
  namespace. Attribution scoring needs those three transcripts re-annotated into real instance
  arrays. A hand-written count table is not a substitute.

## 5. Design

### 5.1 Schema

```ts
export const snuggValuesSchema = z
  .object({
    basedata: BasedataFields.optional(), // singleton, unchanged
    health: HealthFields.optional(), // singleton, unchanged
    hvac: z.array(HvacFields).optional(), // collection
    attic: z.array(AtticFields).optional(),
    wall: z.array(WallFields).optional(),
    window: z.array(WindowFields).optional(),
    dhw: z.array(DhwFields).optional(),
  })
  .strict();
```

Arrays rather than fixed slots. Strict structured output supports arrays with an `items` schema, and
— importantly for [doc 16](../../implementation/16-extraction-schema-scale.md)'s limits — an array
does **not** multiply the property count. One `items` schema, so the extraction schema stays near
today's 211 properties rather than approaching the 5,000 cap.

`enveloped()` must recurse **through** an array into its element schema, wrapping each leaf of each
element. The frozen JSON Schema fixture will move; that is a deliberate field-set change and the one
case `extraction-shape.test.ts` permits, with the same provenance note the last move carried.

### 5.2 Absent vs empty

Three states, and they must stay distinct, mirroring the patch semantics already in place:

| Patch value  | Meaning                                               |
| ------------ | ----------------------------------------------------- |
| key absent   | the reviewer rejected everything here — touch nothing |
| `[]`         | no instances of this type — create none               |
| `[{…}, {…}]` | create/update these instances                         |

### 5.3 Instance identity on write

> **SUPERSEDED by §10.4.** Instance identity is **in scope**. Two spec findings made it far cheaper
> than this section assumed: `hvacUpgradeAction` already carries `"Remove a system permanently"`, so
> the common removal case is extractable data rather than a `DELETE`; and the candidate set is the
> job's own child records, typically one to four, so this is a small-N match rather than a record-
> linkage problem. §10.4 has the resolution policy and the asymmetry that sets it.

**Deliberately out of scope for this design, and separable.** Creating instances (`POST
/jobs/{jobId}/hvac`) needs no identity — a new job creates new records, and
[doc 17](../../implementation/17-snuggpro-field-reconciliation.md)'s owner correction records that
**writes are mostly creates**. Matching a dictated system to an _existing_ uuid is a real problem
(doc 17 §5's first-write identity problem) but it only bites on update, and it needs a design of its
own — probably involving the review card showing the human which existing record a system will land
on. Do not let it block collections.

## 7. Open questions

1. **~~Should review let a human split or merge instances?~~ Resolved (owner, 2026-08-07): the hook
   exposes `addInstance` / `removeInstance` / the existing per-leaf edit, and nothing else.** Split
   and merge are _compositions_ over that basis, not primitives: splitting is an add plus edits;
   merging is edits plus a remove. Keeping the contract to three operations matches the package's
   headless discipline — the hook supplies primitives, the host supplies affordances. If a field app
   wants a one-tap "split this system", it builds it from these.

   Two consequences worth writing down rather than rediscovering:

   - **`removeInstance` must be a real operation, not "reject every leaf".** §5.2 already makes an
     all-rejected instance absent from the patch, which is the correct behaviour on a **create**. But
     the API has `DELETE /jobs/hvac/{uuid}`, so once updates exist the two diverge sharply: rejecting
     every leaf means _leave the existing record untouched_, while removing an instance means _delete
     that record_. Those are opposite instructions, and a reviewer who taps "remove" on a system that
     is not there any more means the second. Synthesising remove from rejections would silently pick
     the wrong one.
   - **Revision 2 claimed a provenance problem here. There isn't one — the claim was wrong and is
     retained only so nobody re-derives it.** It argued that values moved during a split would "land
     ungrounded", losing their `sourceSpan` and forcing the submit gate to demand them again. Both
     halves are false. `resolveReview` returns `fields: Record<string, unknown>` — **plain values**.
     Provenance is stripped at the review boundary by design (R1.5: passing the model's envelopes
     onward "would have made a reviewer's corrections invisible at write time"), so there is no
     downstream evidence trail to lose. And the submit gate tests `untouched` leaves; an edited leaf
     is _touched_, so an edit satisfies the gate rather than re-triggering it.

     What is actually true, and is correct behaviour: a leaf on a newly added instance has no
     extraction, so it carries the sentinel envelope and reads `isGrounded: false` while untouched —
     which means the gate holds until the reviewer fills or rejects it. That is the gate doing its
     job on a human-created instance, not a defect.

     The only residue is ergonomic: splitting means retyping values that are already in the
     transcript. If that proves annoying in the field, seeding a new instance from selected leaves of
     an existing one is a host-side convenience, not a contract change.

2. **~~How does the review card order instances?~~ Resolved (revision 5): first-mention order**, in
   `r1.6-instance-extraction-design.md` §5.2. It matches how auditors narrate and how Snugg itself
   identifies systems ordinally. §10.2 separates it from instance identity: order is presentation,
   the key is what a decision is about. Original text follows.

   Schema-declaration order is meaningless across
   array elements. Extraction order (first-mentioned first) is the obvious answer and matches how an
   auditor narrates, but it should be stated rather than assumed.

3. **~~Does `requiredOnCreate` apply per instance?~~ Resolved (revision 5, §10.3): yes, and it is
   declared per GROUP rather than per path** — exact leaf paths never match a keyed path and so never
   fire. Original text follows.

   **Does `requiredOnCreate` apply per instance?** `hvac.hvacSystemEquipmentType` and
   `hvacUpgradeAction` are required by the API on every HVAC create, so with N systems that is N × 2
   required fields. The review card's required-marker logic is per-leaf-path and should handle this,
   but it has never been exercised against more than one instance.

4. **How many instances is too many?** No cap is proposed. A transcript describing eight systems is
   more likely a segmentation failure than a real house, and a sanity bound may be worth having —
   but as a _review_ warning, not a schema constraint, since a schema constraint would silently
   truncate.

## 8. Sequencing

1. **Core first** — `field-path.ts`, `enveloped.ts`, `review.ts`. Everything depends on these and
   they are the published contract. Land with the array-path and enumeration changes fully tested
   against a synthetic multi-instance schema, before any adapter change.
2. **Adapter schema** — the five collections, plus the normalization pass that guarantees a first
   instance.
3. **Extraction** — instructions and the few-shot example.
4. **Review UI** — instance grouping in the playground.
5. **Scorer** — the instance-count measure, then re-score the corpus.

Steps 1 and 2 are independently testable and independently reviewable. Step 5 is what tells us
whether extraction can actually segment, and it should run before any local-model evaluation, since
segmentation is the reasoning a small model is least likely to do well.

## 9. Revision 4 — what the external design review found

A read-only design review (Codex, dispatched 2026-08-07 before any implementation) found eight
defects. Two were false claims of mine, verified against the code rather than argued:

1. **`childPath` does not reject `[`.** Revision 3 said brackets were safe because it did. It refuses
   `.` and integer-like keys only (`field-path.ts:92,99`). Corrected in §4.1, which now asks for a
   reserved-character rule and one shared parser.
2. **Reassembly cannot see arrays.** `resolveReview` splits on `.` (`review.ts:487`), so an indexed
   path rebuilds as an object with a literal bracketed key. Emitting the syntax was only half the
   change. Added to §6.
3. **`normalization.ts` destroys arrays today.** `clampDeep` rebuilds every object with
   `Object.fromEntries(Object.entries(node))`, which turns `[{x}]` into `{"0":{x}}` — verified in a
   REPL. It would corrupt every collection on the first run, and revision 3's change inventory
   missed it entirely. Added to §6.
4. **The empty-collection placeholder collapses the patch semantics.** §5.2 distinguishes absent,
   `[]` and populated — but after the placeholder is inserted, _no review decision reconstructs `[]`_.
   Accepting its leaves yields `[{all null}]`, which can **create an empty child record**; rejecting
   them yields absent, meaning "touch nothing". Neither says "confirmed, there are none". This is
   worst for `attic`/`wall`/`window`/`dhw`, which have no required-on-create field to stop an
   all-null create. Inferring intent from "every value is null" is unsafe, because `null` is
   deliberately a real writable value. **The placeholder needs explicit instance-level state**
   (synthetic vs model-emitted) with defined resolutions. Unresolved — this blocks §5.2.
5. **Removing an element renumbers every later path**, and review decisions and errors are keyed by
   path, so naïve compaction reattaches a decision to a different physical instance. Needs stable
   review identity or an atomic remap. Unresolved.
6. **`requiredOnCreate` cannot express per-instance requiredness.** It holds exact paths
   (`hvac.hvacSystemEquipmentType`), which never match `hvac[0].…`. §7.3 listed this as an open test
   question; it is actually a contract that must be decided in step 1.
7. **`removeInstance` is not representable** in the patch or the persisted outcome — an array of
   values carries neither deletion intent nor a uuid. So the doc cannot simultaneously claim
   `[{…}]` means "create/update" and that removal has `DELETE` semantics. Either R1.6 is explicitly
   **create-only**, or instance identity comes back into scope. Unresolved.
8. **Instance ordering is not deferrable.** Array indices become public field paths, so the order has
   to be part of the contract before any path is persisted. Moved out of §7's open questions.

**What the review endorsed:** arrays are the right schema shape for repeated child resources;
recursing through the item schema does preserve full leaf enumeration inside each emitted instance;
bracket notation is reasonable _once backed by a real parser and a reserved-character rule_; and
deferring uuid matching is sound **if** the release is explicitly create-only.

**Its summary, which is the right frame for planning:** the blocking work is instance-level _review
state_ — placeholders, add/remove, stable identity during review, required-field matching, and how
those resolve into absent/empty/populated. Without it the design can display arrays but cannot safely
review or write them.

**Status change:** this document is **not ready for implementation**. Items 4, 5, 7 and 8 need
decisions first, and all four are about review state rather than schema shape — which is where the
review says the real design work is.

## 10. Revision 5 — the four blockers, decided

Revision 4 ended by saying the blocking work is instance-level **review state**, and it was right.
This section decides items 4, 5, 6 and 7. Item 8 (ordering) was closed by
[`r1.6-instance-extraction-design.md`](r1.6-instance-extraction-design.md) §5.2: **first-mention
order**, which matches how auditors narrate and how Snugg itself identifies systems ordinally
("System 1", "System N").

The extraction half of §4.3 — segmentation, eligibility and attribution — now lives in that separate
design and is not restated here.

### 10.1 Item 4 — the empty-collection placeholder is deleted, not specified

**Decision: `normalizeFields` inserts nothing. An empty collection stays empty.**

Revision 3 proposed inserting one all-null instance into any empty collection so the group stayed
reviewable, and revision 4 correctly found that this collapses the patch semantics: once a synthetic
row exists, _no review decision reconstructs `[]`_. Accepting its leaves yields `[{all null}]`, which
can create an empty child record; rejecting them yields absent, meaning "touch nothing". Neither says
"confirmed, there are none".

Revision 4 proposed fixing this with explicit instance-level state — synthetic versus model-emitted,
with defined resolutions for each. **We are not doing that.** It resolves the contradiction by adding
machinery to review, when the contradiction only exists because we manufactured a row in the first
place.

Instead the reviewability the placeholder was protecting is supplied at the **group** level. An empty
collection renders as the group with an explicit "none described — add one" affordance. The reviewer
still sees that `hvac` exists and was not addressed, and can still correct a miss, which is the
regression §4.2 identified. But nothing fake is ever inserted, so the three patch states stay exactly
as §5.2 defines them:

| Patch value  | Meaning                                               | How review produces it                 |
| ------------ | ----------------------------------------------------- | -------------------------------------- |
| key absent   | the reviewer rejected everything here — touch nothing | every leaf of every instance rejected  |
| `[]`         | no instances of this type — create none               | the group was left empty and confirmed |
| `[{…}, {…}]` | create/update these instances                         | instances present and accepted         |

**What this costs, stated plainly.** `review.ts`'s "every leaf always appears" property no longer
holds for an empty collection — there are no leaves to show, because there is no instance. That is a
real weakening of the invariant, and it is accepted because the alternative weakens something worse:
inferring "there are none" from "every value is null" is unsafe, since `null` is deliberately a real
writable value meaning "write this field empty". The group-level affordance is what keeps the _group_
from vanishing silently, which is the part that actually protects the auditor.

### 10.2 Item 5 — stable instance keys, not array indices

**Decision: review addresses instances by a stable key, not by position.**

Revision 4's finding: removing an element renumbers every later path, and review decisions and errors
are keyed by path, so naïve compaction reattaches a decision to a different physical instance.

The fix is to stop making position load-bearing. Each instance carries a **key assigned when the
instance enters review** and stable for that review's lifetime — including across add and remove.
Leaf paths address the key, not the index. Removing an instance therefore renumbers nothing: the
remaining keys are untouched and every decision stays attached to the instance a human made it about.

Ordering (item 8, first-mention) is presentation, derived from the instance's position in the emitted
array, and stays separate from identity. That separation is the point: **order is how the card reads;
key is what a decision is about.** Conflating them is what created the renumbering hazard.

The key is review-scoped and does **not** persist into the patch — the patch is positional, because
the API's own instance identity is positional and a create has no key yet. The key exists to make
review decisions addressable, and its life ends when `resolveReview` produces the patch.

**This refines §4.1 rather than replacing it.** The bracketed segment stands, and so does everything
§4.1 asks for — the reserved-character rule on `[`, and one shared grammar used for construction and
reassembly. What changes is what the bracket _carries_: a stable key, not an ordinal. So a leaf path
reads `hvac[k3].hvacDuctLeakage`, not `hvac[0].hvacDuctLeakage`.

Two things fall out of that, both good. A non-integer-like key cannot trigger the property-order
hoisting §4.1 opens with, so the original hazard is gone at the root rather than worked around. And
`resolveReview` gains an explicit **key → position** mapping step when it builds the positional
patch, which is exactly the "atomic remap" revision 4's item 5 asked for — made a named step in the
resolver instead of an invariant everyone must remember.

### 10.3 Item 6 — `requiredOnCreate` becomes per-group, not per-path

**Decision: requiredness is declared per group and applies to every instance of it.**

`requiredOnCreate` today holds exact leaf paths (`hvac.hvacSystemEquipmentType`), which never match an
indexed or keyed path and therefore never fire. Since a record is per instance, requiredness is per
instance by construction: `hvacSystemEquipmentType` and `hvacUpgradeAction` are required on **every**
HVAC create, so a house with N systems has N × 2 required fields.

Declaring the requirement against the group and applying it to each instance is both simpler than
enumerating paths and the only shape that can express "N × 2" without knowing N at build time.

### 10.4 Item 7 — instance identity is in scope, and removal is mostly not a DELETE

**Decision: R1.6 resolves identity. It is not create-only.** Two spec findings make this far cheaper
than revision 4 assumed.

**Removal is usually a field, not a verb.** `hvacUpgradeAction` carries the member
`"Remove a system permanently"`. An auditor saying _"there's an oil boiler here, we should get rid of
it"_ is therefore producing **extractable data**, not a deletion instruction —
[doc 17](../../implementation/17-snuggpro-field-reconciliation.md) already establishes this field as
extracted rather than hard-coded. So `removeInstance` in the review contract maps to a field value for
the common case, and `DELETE /jobs/hvac/{uuid}` is reserved for the genuinely different act of "this
record should not exist at all" — a data-entry correction, always human-initiated, never inferred.
Revision 4's item 7 treated removal as necessarily a DELETE and concluded identity had to come into
scope for it; the vendor already models the common case as data.

**The candidate set is tiny and pre-blocked.** `GET /jobs/{jobId}/hvac` returns only that job's
systems — typically one to four. The record-linkage machinery that exists to avoid N² comparison
across millions of records (blocking keys, LSH, canopy clustering) is unnecessary here. This is a
small-N match already scoped by job.

**The resolution runs at review, never at extraction.** This is the hard constraint and it is not
negotiable: if the job's existing records were placed in the extraction prompt, the model could copy
values out of them and emit them with an invented `sourceSpan`, breaking rule 1's "every value you
emit was said out loud" and the provenance envelope with it. Existing records enter at the review
boundary, after extraction has produced its grounded values.

**The policy, and the asymmetry that sets it.** A wrong **create** leaves a duplicate record — ugly,
visible, fixable in Snugg's own UI. A wrong **link** silently overwrites one appliance's data with
another's, which is precisely this document's own §1 defect moved from within-record to
across-record: individually plausible, invisible to field-level review, and worse for being harder to
see. So create is the safe default and linking must clear a bar:

| Situation                                                                                | Resolution                         |
| ---------------------------------------------------------------------------------------- | ---------------------------------- |
| Exactly one existing record of the type, one dictated instance, **no field contradicts** | link, automatically                |
| Two or more candidates, or two or more dictated instances                                | human picks; **default is create** |
| Any captured identifying field contradicts                                               | create                             |
| No existing records                                                                      | create                             |

**"No field contradicts" is a veto, not a score.** A disagreement on **any** captured identifying
field — equipment type, manufacturer, model, model year — blocks the automatic link. Majority
agreement is not enough. This is what closes the realistic failure: a prior visit recorded the AC and
this visit describes the furnace, where `hvacSystemEquipmentType` disagrees and the link must not
fire.

**The residual risk, stated rather than implied.** With exactly one existing record, one dictated
instance, and no contradicting field, a link happens without a human seeing it. If those are in fact
different appliances that happen to agree on every field we capture, that link is wrong and silent.
The judgement is that this is narrow — R1.6's segmentation means two described systems produce two
instances and fail the "exactly one" test, and the contradiction veto catches differing equipment —
and that the tap it saves on every revisit is worth it. Recorded so a future reader knows it was
chosen rather than missed.

**A language model may propose a correspondence; it never decides one.** Models generate candidate
matches well and calibrate confidence poorly. The deterministic veto above decides.

### 10.5 A hazard this introduces, which must be designed before it ships

**The outbox retries, and the API has no idempotency key.** A create that succeeds but whose response
is lost will create a second record on retry — so identity work introduces a duplicate-record bug
while trying to prevent one. The write step must persist each returned uuid as it arrives and be
**resumable per instance**, not per item, so a retry resumes after the instances already created
rather than replaying them. This is a write-step change, it is not optional, and it does not exist
today. It belongs in the implementation plan as its own task.

### 10.6 What is still deliberately not decided

- **Whether `distinguishedBy` should be required** is decided **yes** in the extraction design, and is
  that document's sharpest trade-off. Recorded here only so the two are not read as disagreeing.
- **How the review card renders instance grouping** stays a host concern. The hook supplies
  `addInstance` / `removeInstance` / per-leaf edit (§7.1) and nothing else.
