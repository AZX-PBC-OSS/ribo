# R1.6 — Instance Extraction — Design

**Date:** 2026-08-27
**Author:** AZX
**Status:** Draft — ready for review
**Task:** **R1.6**, the extraction half of instance modeling — §4.3 of
[`r1.6-instance-modeling-design.md`](r1.6-instance-modeling-design.md), expanded into its own design.
**Authority it corrects:** that document's §4.3, whose proposed segmentation rule ("a separate
physical unit") it rejects, and whose mitigation ("extraction instructions gain a segmentation
rule") it finds insufficient.
**Depends on:** R3 (the per-group extractor), `extractor-arbitration-design.md` (the tiered-strategy
combinator)
**Blocks:** any measurement of whether collections are viable at all

---

## 1. Goal

**The schema will record a sentence about one machine as a fact about another, and every field will
look right.**

That is R1.6's core hazard and it is worth restating precisely, because it is not a data-loss
problem. Given a house with two independent HVAC systems, a single-slot schema produces a record in
which the manufacturer belongs to one appliance and the duct condition to another. Each field is
individually plausible, each is individually true of _something_, and a reviewer scanning the card
sees nothing wrong — because nothing _is_ wrong field by field. Only the combination is a lie, and
field-level review is structurally blind to it.

Making the schema a collection creates somewhere for the second system to live. It does not make the
model put the right facts in the right element. **This design is about the second half.**

## 2. The problem is referent resolution, and it has three independent parts

The parent design frames this as segmentation. That framing is too coarse: it fuses three
sub-problems that fail independently, need different mechanisms, and must be measured separately or
a fix to one will be read as a fix to another.

| Sub-problem     | The question                                                   | Failure looks like                                      |
| --------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| **Enumeration** | How many recordable instances of each resource type exist?     | Two systems merged into one; one system split into two  |
| **Eligibility** | Which mentioned components belong in the record at all?        | A decommissioned or off-property unit logged as current |
| **Attribution** | Which mention, and so which value, attaches to which instance? | The false-but-plausible record of §1                    |

Today's single-slot schema collapses all three into "fill the form", which is exactly why they are
indistinguishable when they go wrong. A run can get the count right and the attribution wrong; that
combination is the parent design's revision-4 finding that an instance-count metric "passes the exact
defect R1.6 exists to fix."

**Eligibility is not noise-filtering.** An auditor who says _"do not log the old boiler"_ is making a
judgement and stating it out loud. Treating it as a filter step throws away the fact that a judgement
was made, which is the difference between a system that was considered and excluded and one that was
never seen.

## 3. The principle this is built on

`ribo-core`'s provenance envelope grounds a **value**: rule 3 says a value without a verbatim
`sourceSpan` has no grounds and must be `null`, because a fabricated quote "destroys the one
mechanism the auditor has for checking you."

**Nothing today grounds a record's existence.** An instance the model invents is a fabricated record —
a whole appliance that does not exist, carrying a full set of individually-plausible fields — and it
is currently easier to emit than a single fabricated value. That asymmetry is the generic gap, and
closing it needs no new doctrine: it is rule 3 applied one level up.

The design therefore uses **one mechanism three times**. Each of §2's sub-problems is guarded by
requiring a verbatim span:

| Sub-problem    | Guard                                                                                   |
| -------------- | --------------------------------------------------------------------------------------- |
| **Existence**  | An instance needs the span that introduces it.                                          |
| **Separation** | A second instance needs the span where the auditor distinguishes it.                    |
| **Exclusion**  | Declining to record a mentioned component needs the span where the auditor excludes it. |

Each guard makes the _unsafe_ direction require evidence and the _safe_ direction free. A model
cannot invent a system, cannot split one system into two, and cannot quietly drop a live one, without
quoting the auditor doing it.

## 4. The enumeration criterion

### 4.1 A rejected criterion, recorded so it is not re-proposed

An earlier draft proposed: _two mentions are one record iff the group's identity-bearing fields would
take the same value for both_ — for `hvac`, `hvacSystemEquipmentType`, which already encodes the
distribution axis.

**It is circular and it does not decide the common case.** The identity-bearing field's _value_ is
extraction output, so applying the test requires having already filled the records whose number the
test is supposed to determine. And it is silent on the ordinary case: _"the upstairs HVAC is furnace
based"_ followed by _"the upstairs HVAC is large"_ asserts no identity-bearing field on the second
mention at all, so the predicate is undefined and the safe-looking default is to split — the failure
mode we care most about.

It is also neither necessary nor sufficient. Two identical furnaces, upstairs and down, share an
equipment type and are two records. A self-correction changes the equipment type and is one.

### 4.2 What replaces it: two rules at different levels

The mistake was fusing a linguistic question with a vendor question.

**Rule A — co-reference. Generic, model-native, no schema involvement.**
Every mention refers either to a component already in the roster or to a new one, and **the default is
already in the roster**. The auditor individuates however they like — location (_"the upstairs one"_),
brand (_"the Lennox"_), fuel, function (_"heating"_), ordinal, or deixis — and the roster records
whichever axis they actually used, in their words. This is the task a language model is genuinely
best at; constraining the axis to a typed field asks it to do a harder and more artificial thing, and
breaks the moment an auditor individuates by something the schema does not model.

**Rule B — granularity. Vendor-specific, one statement per group, not a per-mention predicate.**
What the vendor counts as _one record_. For `hvac`: equipment sharing a distribution system is one
record even when it is several physical boxes — the enum member
`"Furnace / Central AC (shared ducts)"` is one record covering a furnace and a condenser — while
equipment with its own distribution is another. Stated once per group with contrastive examples that
pin the coarseness, and nothing more.

This is where the parent design's objection to "a separate physical unit" is answered: an air
handler, a condenser and a plenum are parts of a system, not systems, and Rule B is the statement
that says so.

### 4.3 Merge by default

The load-bearing property is the direction of the default. **Merging is free; splitting requires
evidence.**

- _"The upstairs HVAC is large"_ merges with no work, because nothing distinguishes it.
- Over-segmentation — the hallucination surface the parent design worries about — now requires the
  model to point at explicit distinguishing language.
- It matches the shape of the eligibility rule, where inclusion is default and exclusion needs a
  quote. One direction of caution, applied consistently.

The instructions name what counts as evidence each way. **Splitting evidence:** explicit contrast
(_"separate from"_, _"its own"_, _"standalone"_, _"the other one"_, _"a second"_), stated
coexistence, attributes that cannot hold of one thing concurrently, or an explicit count.
**Merging evidence:** a bare re-mention, a pronoun or definite description continuing the current
topic, a part-whole mention (Rule B), or a correction marker (_"no wait"_, _"actually"_, _"I mean"_),
which signals sequential revision rather than coexistence.

**A typed-field contradiction is deliberately not used as a tiebreak.** _"It's a boiler"_ then _"it's
a heat pump"_ is either a split or a self-correction, and the signal cannot tell them apart. It is
also still circular. Bolting a weak circular signal onto a clean rule is how a prompt rots.

## 5. Design

### 5.1 Topology — one house-wide inventory pass, then scoped per-instance fills

```
call 1        inventory(transcript)   → roster for all five collection groups
call 2 … k    fill(group, instance)   → one per current instance, concurrent
call k+1, k+2 fill(basedata), fill(health)  → singletons, unchanged
```

The inventory pass is **house-wide rather than per-group** because the miscategorisations that matter
most cross group boundaries and no per-group call can see them: an attic air handler is an `hvac`
instance and not an `attic` one; a sidearm tank off the boiler is a `dhw` instance whose fuel belongs
to an `hvac` instance. A per-group call is never shown the alternative, so no amount of within-group
prompting recovers those. The roster schema carries no leaf fields, so it stays far inside the size
caps that forced R3's split in the first place.

Cost: **7 calls today, `1 + N + 2` after** — 8 for a house with one of everything, 9 with a second
HVAC system. Roughly flat. The honest price is **one extra serial round-trip of latency on every
extraction**, because the fills cannot fan out until the roster exists. The fills themselves
parallelise exactly as R3's groups do, on the same bounded pool.

### 5.2 The roster

Per candidate instance, five fields. Three of them are the §3 guards.

| Field             | Purpose                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `mentionSpan`     | Verbatim substring introducing the component. **Grounds its existence.**                                      |
| `discriminator`   | Short auditor-language handle. A prompting artefact with no write target.                                     |
| `distinguishedBy` | Verbatim span separating this candidate from earlier ones. `null` for a group's first. **Grounds the split.** |
| `eligibility`     | `current`, or a named exclusion reason — `decommissioned`, `proposed`, `off-property`, `outside-scope`.       |
| `eligibilitySpan` | Verbatim quote for any non-`current` verdict. **Grounds the exclusion.**                                      |

A group the transcript never touches yields an empty list.

**`discriminator` is free text on purpose, and has no write target on purpose.** Doc 12 shows Snugg
Pro's own UI labels systems ordinally — _"System 1 Duct Work"_, _"System N"_ — so the vendor's
instance identity is positional, not nominal. There is no name field in our subset or in the API to
carry it. Inventing a leaf for it would repeat the `atticInsulationSpokenRValue` holding-pen mistake
that R1.6's vocabulary half already deleted.

**Ordering is first-mention.** That matches how auditors narrate and how the vendor identifies
systems, and it closes the parent design's revision-4 item 8 — _instance ordering is not deferrable,
because array indices become public field paths_ — with a stated rule rather than an assumption.

**Instance-level self-correction needs its own rule.** Rule 5 (_"the last assertion wins"_) governs
values. A retraction that changes the **count** — _"there's an air handler, no wait, the furnace is
in the closet and the AC air handler's the separate thing"_ — resolves to the post-correction
enumeration. Same principle, different level, and it must be stated separately or rule 5 will be
applied to a question it does not address.

### 5.3 The roster is internal

The roster is **scaffolding for prompt assembly, not part of the extraction contract**. It is not
persisted, does not enter `ExtractionResult`, and does not reach review. Decided deliberately; the
consequences, stated plainly:

- **Recovered for free.** Permutation-insensitive scoring does not need a persisted key — the scorer
  bipartite-matches predicted to true instances by maximising leaf agreement. See §7.
- **A genuine accepted loss.** An eligibility decision leaves no trace. If the model wrongly excludes
  a live system, nothing anywhere says so, and it is indistinguishable from a system never mentioned.
  That is the same silence the provenance envelope exists to forbid, one level up. It is accepted
  here because surfacing it means a core contract change and a review-card affordance, and both are
  additive later. **Recorded as a known gap, not as a solved problem.**

### 5.4 The scoped fill call — the actual anti-mixing mechanism

Each `current` candidate gets one call against **today's flat group schema, entirely unchanged**.
`HvacFields` never becomes an array from the model's point of view. It stays the exact shape R3
already sends, with its existing rules, its vendor descriptions and its frozen-fixture discipline
intact. Only prompt assembly changes, by adding a scope block between the rules and the transcript:

- **Positive identity** — which record is being filled, named by its `discriminator`, with the
  `mentionSpan` that introduced it.
- **Negative siblings** — the other instances of this type, by discriminator and span, declared out
  of scope, **with the explicit assurance that their facts are being captured on their own records**.
- **Excluded candidates** — named with their `eligibilitySpan`, to be recorded nowhere.

**The negative-sibling block is why this topology is worth its extra round-trip.** Today the model
holds one slot and a fact that must go somewhere, and emitting `null` reads as a loss. That pressure
is what produces the false-but-plausible record. Once siblings are explicit and the model is told the
fact lands elsewhere, `null` becomes _correct routing_ rather than a miss. Prose rules inside a single
undivided call cannot create that, because in that call the alternative slot does not exist.

Two structural properties follow:

- **The fill call cannot disagree with the roster.** Its response schema is a single object, not an
  array, so it has no way to add or drop an instance. Segmentation is decided exactly once.
- **The fill call sees the whole transcript**, never a filtered slice. Auditors back-reference freely
  across paragraphs; a filtered view would trade the mixing bug for a truncation bug.

### 5.5 Assembly and bounds

Fill results collect into their group's array in roster order. `basedata` and `health` stay singletons
on today's path. R3's bounded per-group retry generalises to per-**call** (group plus index)
unchanged.

An instance cap exists as a cost and latency guard and **fails loudly rather than truncating**,
because truncating drops a real system silently — which is the class of bug this whole task exists to
remove.

An empty collection is emitted honestly as empty. What review does with that is the parent design's
§4.2 placeholder problem, which is review-side and out of scope here (§9).

## 6. Failure — the tiered strategy ladder

The inventory pass is a single point of failure for the whole extraction, which is the property R3
deliberately engineered away at group level. Rather than accept that or degrade silently, the
extractor is a **ladder of strategies** run through `fallbackExtractor`
(`extractor-arbitration-design.md`):

| Tier | Strategy                                           | Isolation                                                        |
| ---- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 1    | House-wide inventory → scoped per-instance fills   | Structural — one slot per call, siblings explicitly out of scope |
| 2    | Per-group call, model emits an array               | Prose rules only, single undivided attention                     |
| 3    | Per-group call, flat singleton (today's behaviour) | None — cannot represent a second instance                        |

Tier 2 is the option considered and set aside in favour of tier 1: it answers the same question with
weaker isolation. Tier 3 answers a smaller question and **cannot represent the case this task exists
to fix** — it is on the ladder anyway, because for a deployment with an auditor in a basement and no
connectivity, a single-instance record may be better than no record.

**That judgement is the host's, made through the arbiter's exhaustion call, not the SDK's.** An
earlier revision of this design proposed an invariant forbidding tier 3; that was the wrong layer,
and `extractor-arbitration-design.md` §2 records why.

Trigger discipline is §4.3 of that design: transient failures exhaust the candidate's own retry
budget first, terminal failures move on immediately without retry, and a schema-parse failure moves
on — the last being the likeliest tier-1 failure, since the roster is a response shape no model has
been asked for before.

**The accepted tier lands on `usage.strategy`.** A fallback nobody can see is a quality collapse that
reads as success, and §7's numbers are uninterpretable without it.

## 7. Measurement — three metrics, because three failure modes

Reporting one number here would repeat the parent design's revision-4 defect in a new place.

1. **Enumeration** — predicted against true instance count per group, reported with direction, so
   over- and under-segmentation are never averaged into each other.
2. **Eligibility** — for each mentioned-and-excluded component, was it excluded, and for the stated
   reason. Scores the judgement, not just the outcome.
3. **Attribution** — bipartite-match predicted to true instances by maximising leaf agreement, then
   score leaves within each matched pair. **Permutation-insensitive by construction**, so a run
   emitting the same two systems in the other order is not penalised while genuine cross-instance
   mixing goes unnoticed. Unmatched instances report separately: a predicted instance with no match is
   a fabrication; a true instance with none is a miss.

All three are reported **alongside the tier distribution** from §6. A run in which 40% of items fell
to tier 2 is a different number from one where none did, and without the tier they are
indistinguishable.

**Dependency, stated as a dependency and not as evidence:** none of this is measurable until the
corpus ground truth carries instance arrays. Its leaf records are single-instance by construction,
and the multi-system transcripts encode their collisions in prose `notes` because that is all the
format could express. The corpus is also **generated**, so it is a source of hazard _shapes_ — an
existence proof that a construction occurs and can be handled — and never a source of _rates_. No
part of this design is justified by how often something appears in it.

## 8. On-device

Same topology, no special case. The inventory pass is a reasoning task and therefore the hardest
thing to ask a ~3B model, so the segmentation gap is measured before the on-device path is enabled
for collection groups.

**It must not silently fall back to a single instance.** That would reintroduce the exact defect,
invisibly, on precisely the path with no network available to check it. If tier 1 is beyond an
on-device model, that engine's ladder simply starts at tier 2 — a composition the arbitration design
supports directly, since ladders differ per engine.

## 9. Out of scope

Named so the boundary is explicit, and because this design deliberately does **not** unblock the
parent document.

- **The four revision-4 blockers** — placeholder semantics for an empty collection, path renumbering
  on removal, `removeInstance` representability, and instance ordering in review. All four are
  _review-state_ problems. This design supplies §5.2's ordering rule, which closes item 8's input;
  the other three are untouched and still block the parent design.
- **Instance identity on write.** Matching a dictated system to an existing uuid. Still deferred,
  still create-only.
- **Surfacing eligibility to review.** §5.3's accepted loss. Additive later.

Extraction can be built and measured without any of these, and should be — it is what tells us
whether the model can segment at all, which every downstream decision depends on.

## 10. Sequencing

1. **The arbitration combinator** (`extractor-arbitration-design.md`). Nothing here composes without
   it.
2. **The roster schema, instructions and inventory call.** Independently testable against a synthetic
   multi-instance target before any adapter change.
3. **Scoped fill assembly.** The scope block and the negative-sibling text. The fill schema itself is
   untouched, so the frozen fixture does not move at this step — a useful checkpoint.
4. **Corpus re-annotation into instance arrays.** Manual, and the reason the baselines are
   trustworthy. Blocks all of §7.
5. **The three scorers**, then re-score.

Step 5 is what tells us whether extraction can segment. It should run before any local-model
evaluation, since segmentation is the reasoning a small model is least likely to do well.

## 11. Open questions

1. **How much of the transcript does the inventory pass need?** It is given the whole thing today by
   default. If roster quality is insensitive to the leaf-level detail, a cheaper inventory is
   available; if it is sensitive, that is worth knowing before optimising anything.
2. **Should `distinguishedBy` be required, or strongly encouraged?** Required makes splitting
   structurally impossible without evidence, which is the point. It also means a genuine two-system
   house where the auditor never explicitly contrasts them collapses to one record. Proposed:
   required, on the grounds that under-segmentation is recoverable at review and a fabricated record
   is not — but this is the design's sharpest single trade-off and it should be measured rather than
   assumed.
3. **Does the eligibility vocabulary generalise past `hvac`?** `decommissioned` and `proposed` are
   equipment concepts. Whether an attic or a wall assembly is ever "decommissioned" is unclear, and
   the reason set may need to be per-group like Rule B.
