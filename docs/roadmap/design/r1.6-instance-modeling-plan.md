**Scope.** One increment covering all five collection groups end to end: schema, extraction, review,

## Seven decisions pinned. Do not re-open these mid-task.

1. **There is no automatic link.** Every link of a dictated instance to an existing API record is an
   explicit human decision. Ranking and a contradiction check may order candidates; nothing links
   without a human act. An earlier draft auto-linked and an external review showed it silently
   overwrites one appliance's record with another's when extraction under-segments.
2. **No placeholder instance, ever.** `normalizeFields` inserts nothing into an empty collection.
   Reviewability for an empty group is a group-level affordance, not a manufactured row.
3. **Leaf paths carry a stable key, not an ordinal** — `hvac[k3].hvacDuctLeakage`. Order is
   presentation; the key is what a decision is about.
4. **Existing API records never enter the extraction prompt.** They enter at the review boundary
   only. This is the provenance boundary and it is not negotiable — a model shown existing records
   can copy values and emit an invented `sourceSpan`.
5. **`ToolAdapter.write` does not change.** It is a published contract carrying R1.5's `schema.parse`
   trust boundary. Per-instance writing is a new composition beside `toWriteStep`, not a change to
   the adapter seam.
6. **`distinguishedBy` is required to split an instance.** A second instance needs a verbatim span
   where the auditor distinguishes it. This is the extraction design's sharpest trade-off and it is
   decided.
7. **Instance ordering is first-mention.** Not schema order, which is meaningless across array
   elements.

## Task 1 — The path grammar: one parser, keys not indices

**Files:** `packages/ribo-core/src/field-path.ts` and its test.
**Depends on nothing. Start here** — review and the adapter both build on it.

**Intent.** `childPath` currently throws on integer-like keys, with a doc comment explaining that
such a key would be hoisted in JavaScript property order and silently reorder a review card. That
guard stays. Collections get a distinguishable bracketed segment carrying a **stable key**, so the
hoisting hazard cannot arise at all — a non-integer key is not hoisted.

Emitting the syntax is half the change. Modeling design §4.1: `resolveReview` reassembles with
`path.split(".")`, so an unparsed bracketed path rebuilds as an object whose key is the literal text
`hvac[k3]`. **Construction and parsing must share one implementation** with distinct object-key and
instance-key segment types, or they will disagree — and they will disagree silently, producing a
patch shaped nothing like the schema.

**Interfaces.** A path is a sequence of segments, each either an object key or an instance key. One
function builds, one parses, and they round-trip. Decide the exact shape and state it in your report
— Tasks 6 and 7 both consume it.

**Must-fail tests.**

- `childPath` rejects `[` in an **object key**, the way it already rejects `.`, and for the same
  reason: a key that can impersonate a path segment makes the path address the wrong thing.
- Integer-like object keys are still rejected — the existing guard is not weakened.
- A path with an instance-key segment round-trips: build → parse → build yields the identical string,
  and parse yields segments distinguishing the instance key from the object keys.
- A path whose object key contains a bracket cannot be constructed, so no path can be ambiguous.
- **Parsing `hvac[k3].hvacDuctLeakage` yields three segments, not one string key.** This is the test
  that would catch a parser that only pretends to understand the grammar.

## Task 2 — `enveloped()` recurses through arrays

**Files:** `packages/ribo-core/src/enveloped.ts` and its test.
**Depends on nothing.**

**Intent.** `enveloped()` throws on arrays today. It must recurse **through** an array into its
element schema, wrapping each leaf of each element in the provenance envelope. Modeling design §5.1:
an array does not multiply the property count — one `items` schema — which is what keeps the
extraction schema near today's size rather than approaching the documented 5,000-property cap.

**Must-fail tests.**

- An array-of-objects group yields an array whose element carries an envelope per leaf, not one
  envelope for the array.
- Property count does not grow with instance count — assert the derived schema's property count is
  independent of any data.
- A nested array inside an element behaves consistently or is refused explicitly; whichever you
  choose, it is tested rather than incidental.

## Task 3 — `splitExtractionSchema` unwraps arrays

**Files:** `packages/ribo-extractor-openai/src/split-schema.ts` and its test.
**Depends on nothing. Land this BEFORE Task 5** — see below.

**Intent.** This is a landmine no design revision noticed until external review. Group detection is
`value instanceof z.ZodObject && isGroupObject(value)`. The moment `hvac` becomes an array, that
property is a `ZodArray`, `everyKeyIsGroup` goes false, and the function **silently falls back to
returning the whole schema as one entry** — which is over the 32,768-character cap the per-group
split exists to stay under. The failure surfaces as a size error at request time, far from its cause,
and looks like a model or endpoint problem.

Teach the detector to unwrap `ZodArray` into its element schema for the purpose of deciding what a
group is.

**Must-fail tests.**

- A schema whose groups are arrays still splits into one entry per group. **This is the test the task
  exists for**; without it the regression is invisible until an unrelated request fails on size.
- The whole-schema fallback still fires for a genuinely non-grouped schema — the fix narrows nothing
  it should not.
- Each per-group schema derived from an array group stays under the serialized cap, asserted against
  the real adapter schema rather than a toy.

## Task 4 — `clampDeep` stops destroying arrays

**Files:** `packages/ribo-adapter-snuggpro/src/normalization.ts` and its test.
**Depends on nothing.**

**Intent.** `clampDeep` rebuilds every object with `Object.fromEntries(Object.entries(node))`, which
turns `[{x}]` into `{"0": {x}}`. It would corrupt every collection on the first run. Revision 4 found
this; it is still unfixed.

**Also: this task inserts nothing.** Pinned decision 2. If you find a design paragraph asking
`normalizeFields` to insert a placeholder instance, it is §4.2, it is marked superseded, and §10.1
explains why.

**Must-fail tests.**

- An array survives `clampDeep` as an array, with element identity and order intact.
- Confidence clamping still applies **inside** array elements — the recursion reaches them.
- An empty collection stays an empty array and does not become an object or gain an element.

## Task 5 — The five groups become collections

**Depends on Tasks 2 and 3.**

**Intent.** `hvac`, `attic`, `wall`, `window` and `dhw` become arrays. `basedata` and `health` stay
singletons — they are genuine singletons in the API.

**The frozen fixture moves, and that is the point.** `extraction-shape.test.ts` pins the derived JSON
Schema byte-for-byte so a derivation change cannot happen silently. This is a deliberate field-shape
change, which is the one case the fixture permits — update it and carry the same kind of provenance

**Must-fail tests.**

- `snuggValuesSchema` accepts multiple instances per collection group and rejects a bare object where
  an array is expected.
- `basedata` and `health` still reject arrays — the singleton/collection split is asserted, not
  assumed.
- The derived extraction schema still fits the per-group cap (this is Task 3's guarantee, re-asserted

**Two walkers break on arrays and neither is obvious** (found by external review, GLM 2026-08-27):

- `collectLeafDescriptions` in `extraction-shape.test.ts` reads `groupSchema.properties` for every

## Task 6 — Review enumerates instances from data, leaves from schema

**Files:** `packages/ribo-core/src/review.ts` (`buildReviewRequest`) and its test.
**Depends on Tasks 1 and 5.**

**Intent.** `review.ts`'s invariant — "the schema enumerates the leaves, not the data" — is restated,
not abandoned: **the data determines how many instances exist; the schema determines every leaf
within each instance.** That preserves the property that matters (no leaf of a present instance can
silently vanish) while accepting that instance count is necessarily data-driven.

Each instance is assigned a **stable key** as it enters review, and leaf paths address the key.
Ordering is the emitted array order, which the extraction design makes first-mention.

**Also record which groups were present-but-empty.** Task 7 needs that distinction to emit `[]`
rather than absence, and this is the only place it is available — `ReviewRequest` is built from the
extracted data, which knows the difference between `hvac: []` and no `hvac` key. Downstream, the
per-leaf decisions never carry it.

**Must-fail tests.**

- Two HVAC instances produce two full sets of HVAC leaf paths, each addressing a distinct key.
- **Every leaf of every present instance appears**, including leaves the model left null — the
  anti-silence property, asserted per instance rather than per group.
- An empty collection produces no leaf paths **and** is recorded as present-but-empty.
- A group absent from the extraction output is not recorded as present-but-empty. The two must be
  distinguishable or Task 7 cannot work.
- Instance order in the request follows the emitted array order.

## Task 7 — `resolveReview` reassembles arrays, and produces the three patch states

**Un-skip what you unblock.** `skip-inventory.test.ts` records two `round-trip.test.ts` tests as
yours: the full schema → extraction → review → write round-trip, and "one rejected leaf of the 51
still writes the other 50". Delete both skips and both inventory rows. The inventory test fails if
you do one without the other.

**Files:** `packages/ribo-core/src/review.ts` (`resolveReview`) and its test.
**Depends on Task 6.**

**Intent.** Reassembly must use Task 1's parser, not `path.split(".")`. It maps **key → position**
when building the positional patch — a named step, which is the "atomic remap" revision 4 asked for.
The patch is positional because the vendor's own instance identity is positional and a create has no
key yet.

The three states, and each must be reachable:

| Patch value  | Meaning                                           | Produced by                                        |
| ------------ | ------------------------------------------------- | -------------------------------------------------- |
| key absent   | reviewer rejected everything — touch nothing      | every leaf of every instance rejected              |
| `[]`         | no instances — create none, touch none that exist | the group was present-but-empty (Task 6) on submit |
| `[{…}, {…}]` | create/update these instances                     | instances present and accepted                     |

**Must-fail tests.**

- A keyed path rebuilds as `{ hvac: [{…}] }`, **not** as an object whose key is the literal text
  `hvac[k3]`. This is the defect revision 4 found and the reason Task 1 exists.
- An instance whose every leaf was rejected is **absent from the patch**, not present as an instance
  of nothing — otherwise reviewing a house with no water heater `POST`s an empty `dhw` record.
- A present-but-empty group yields `[]`.
- A group absent from extraction yields **no key**, and `[]` and absent are asserted as different
  patches in the same test, since they are opposite write instructions.
- **Removing an instance does not reattach another instance's decisions.** Remove the first of three
  and assert the remaining two carry the decisions their own keys were given. This is revision 4's
  item 5 and the whole reason for stable keys.
- Two instances resolve to positions in first-mention order.

## Task 8 — `requiredOnCreate` becomes per-group

**Files:** `packages/ribo-adapter-snuggpro/src/adapter.ts`, `packages/ribo-core/src/review.ts` where
requiredness is applied, and their tests.
**Depends on Task 7, not merely Task 6.** Task 7 also edits `review.ts`; running them in parallel
puts two engineers in one file, which is the collision class that already bit this project once when
two parallel tasks edited the same barrel without seeing each other. Serialise them.

**Intent.** `requiredOnCreate` holds exact leaf paths today (`hvac.hvacSystemEquipmentType`), which
never match a keyed path and so never fire. A record is per instance, so requiredness is per instance
by construction: N systems means N × 2 required fields for HVAC. Declaring against the **group** is
the only shape that expresses that without knowing N at build time.

**Must-fail tests.**

- With two HVAC instances, both instances' required leaves are marked required — four markers, not
  two, and not zero.
- Singleton groups are unaffected.

**The "submit gate blocks" test does NOT belong here** (found by external review, GLM 2026-08-27).
`resolveReview` checks completeness and value validity; it never reads `ReviewField.required`. The
required flag is surfaced for rendering, and the gate that blocks on an unactioned required leaf is a
UI concern. Core tests that the flag is **set** on both instances; Task 15 tests that the gate acts
on it. Conflating them produces a core test that cannot be written.

## Task 9 — The inventory pass

**Files:** new roster schema and instructions in `packages/ribo-adapter-snuggpro/src/`, a new
extraction phase in `packages/ribo-extractor-openai/src/`, and their tests.
**Depends on Task 5.** (Not Task 3 — the inventory pass builds its own roster schema and never
touches `splitExtractionSchema`. Task 10 is what needs Task 3.)

**Intent.** One house-wide call returning, per collection group, an ordered list of candidate
instances. House-wide rather than per-group because the miscategorisations that matter cross group
boundaries — an attic air handler is an `hvac` instance, not an `attic` one — and no per-group call
is ever shown the alternative.

Per candidate: `mentionSpan` (grounds existence), `discriminator` (auditor-language handle, no write
target), `distinguishedBy` (grounds a split; null for a group's first), `eligibility`, and
`eligibilitySpan` (grounds an exclusion).

The three span requirements are one mechanism used three times, and they are what make the unsafe
direction cost evidence: a model cannot invent a system, split one into two, or drop a live one
without quoting the auditor doing it.

**Instructions carry two rules the schema cannot express**: merge-by-default co-reference (the
default is that a mention refers to something already in the roster), and a one-sentence per-group
granularity rule (what the vendor counts as one record — equipment sharing a distribution system is
one record even when it is several boxes).

**Must-fail tests** — all against fake chat responses, no model:

- A roster entry without `mentionSpan` is rejected by the schema.
- A second candidate in a group without `distinguishedBy` is rejected; the first with `null` is
  accepted.
- A non-`current` eligibility without `eligibilitySpan` is rejected.
- A group the transcript never mentions yields an empty list, not a candidate.
- The assembled prompt keeps the transcript **last** — the injection boundary depends on it, and R3
  pinned that ordering.

## Task 10 — Scoped per-instance fills, and assembly

**Un-skip what you unblock.** `skip-inventory.test.ts` records the on-device extraction badge test
as yours; the three-phase on-device extractor still emits flat group objects.

**Files:** the per-instance extractor in `packages/ribo-extractor-openai/src/`, prompt assembly in
`packages/ribo-adapter-snuggpro/src/instructions.ts`, and their tests.
**Depends on Task 9.**

**Intent.** Each `current` candidate gets one call against **today's flat group schema, unchanged** —
`HvacFields` never becomes an array from the model's point of view. Only assembly changes, by adding
a scope block between the rules and the transcript: positive identity, **negative siblings** declared
out of scope with the assurance their facts are captured on their own records, and excluded
candidates named with their exclusion quote.

The negative-sibling block is why this topology is worth its extra round-trip. Today the model holds
one slot and a fact that must go somewhere, and `null` reads as a loss; once siblings are explicit,
`null` becomes correct routing.

**Must-fail tests.**

- The fill call's response schema is a **single object**, so a fill cannot add or drop an instance —
  segmentation is decided once, in Task 9.
- The scope block names sibling discriminators and spans, and names excluded candidates.
- The fill call receives the **whole transcript**, not a slice. Auditors back-reference across
  paragraphs; a filtered view trades the mixing bug for a truncation bug.
- Results assemble into their group array in roster order.
- The few-shot example in `examples.ts` carries a **second system**, and the assembled prompt still
  matches it — an example showing one system teaches the shape this task exists to move away from.
  Note the example is typed `SnuggExtraction`, so after Task 5 its collection groups change from an
  object to an **array**; that is a shape change, not just an added element, and typecheck will say
  so.
- Exceeding the instance cap **fails loudly** rather than truncating — a truncated collection drops a
  real system silently, which is the bug class this whole task exists to remove.
- A group with no `current` candidates makes no fill calls and yields an empty array.

## Task 11 — Identity: read existing records, rank, human decides

**Files:** `packages/ribo-adapter-snuggpro/src/adapter.ts` (reading existing instances, the
contradiction check), `packages/ribo-core/src/review.ts` and `packages/ribo-ui-react/src/use-review.ts`
(surfacing the decision), and their tests.
**Depends on Task 7.**

**Intent.** At review, each dictated instance is shown alongside the job's existing records of that
type. The human links it to one or creates a new record. **Nothing links automatically** (pinned
decision 1). A deterministic contradiction check — any disagreement on any captured field demotes a
candidate — may order the list, and the strongest may be pre-highlighted, but the decision is a human
act.

**The provenance boundary is the load-bearing constraint here** (pinned decision 4). Existing records
enter at review, never at extraction. Any ranking model is a separate review-time call whose output
is an **ordering**, never field values, so it cannot produce anything carrying a `sourceSpan`.

**Must-fail tests.**

- **Existing records never reach the extraction prompt.** Assert structurally — `Extractor<F>` is
  `extract(transcript: string)`, so a type-level assertion that it takes nothing else catches the
  obvious violation — rather than by inspecting a prompt string. A string assertion passes the day
  someone adds a new call site. **Residual, stated because the test does not close it:** a caller
  could still capture existing records in a closure when constructing the extractor, without changing
  any signature. The structural test does not see that. It is strictly better than a string
  assertion, not a proof.
- A patch resolves to a link **only** when a link decision was made; with no decision, the instance
  resolves to a create. Exactly one existing record with a perfect field match still creates, absent
  a decision. This is the test that would catch someone reintroducing the auto-link.
- A contradicting field demotes a candidate in the ordering.
- A link decision survives `resolveReview` and reaches the patch as an update target.

## Task 12 — Per-instance write resumability

**Files:** a new composition beside `packages/ribo-core/src/write-step.ts`,
`packages/ribo-core/src/queue/schema.ts`, and their tests.
**Depends on Tasks 5 and 11.**

**Read this section carefully — an earlier draft of it was impossible.** It said "persist each
returned uuid before moving on" while also pinning that `ToolAdapter.write` does not change.
`write` is `(fields, ctx, meta) => Promise<void>` (`adapter.ts:222`). **It returns nothing.** There
are no uuids to persist, and `write-step.ts:74` says so outright: "Nothing is returned to the relay:
`ToolAdapter.write` resolves `void`, so there is no `writeResult` to persist." Found by external
review (GLM, 2026-08-27).

**And the machinery this needs already exists, which the design missed.** `WriteMetadata` carries an
`idempotencyKey` (`adapter.ts:108-116`), documented as **stable across every retry of this queue
item**, generated once with the item by the queue, and sent as `Idempotency-Key` precisely so "a
retry after an ambiguous success (the request landed, the response did not) is recognised by the host
tool as the same write rather than a second one." The design's claim that "the API has no idempotency
key" was about the vendor spec and was never checked against our own contract.

**So the mechanism is a derived key, not uuid tracking, and pinned decision 5 survives intact.**

**Intent.** `toWriteStep` calls `adapter.write` once with the whole patch and holds no outbox handle.
Build a **sibling composition** — `toWriteStep` stays — that loops the patch's collection groups and
calls `write` once per instance.

Each per-instance call receives a **derived idempotency key**: a deterministic function of the item's
key, the group, and the instance's position. Deterministic is the whole point — the same instance
derives the same key on every retry, so an ambiguous success is recognised rather than duplicated.

**The per-item key is the wrong granularity and using it directly would be a new bug.** One key
across N creates means that a vendor which honours the header treats instance 2 as a duplicate of
instance 1, and a house with three systems silently becomes one record. Deriving per instance is not
an optimisation; it is what makes collections writable at all.

**Vendor support is unverified**, which is why position tracking is also needed rather than instead.
Doc 17 does not document `Idempotency-Key` on these endpoints. So: derived keys make a retry correct
if the header is honoured, and a persisted record of which instances were already attempted narrows
the window if it is not. The outbox schema gains that per-instance progress record beside
`writeResult`.

**Wiring changes and the plan should not pretend otherwise.** Host wiring today is
`createRelay({ write: toWriteStep(adapter) })`. The sibling composition needs outbox access to
persist progress mid-write, so its construction takes more than the adapter. Decide the shape and
state it in your report.

**State the residual in the code comment.** If the vendor ignores `Idempotency-Key`, a crash between
the API creating a record and our persisting that instance's progress duplicates on retry. That
window narrows but never closes without server-side support. A comment claiming otherwise would be
false.

**Must-fail tests.**

- Each instance's derived key is **stable across retries** and **distinct between instances**. Both
  halves in one test: stable-but-shared silently collapses a collection to one record, and
  distinct-but-unstable defeats idempotency entirely.
- A write that fails on the **second** of three instances, then retries, does **not** re-attempt the
  first. Assert the transport saw one create for instance one across both attempts.
- Progress is persisted **before** the next instance is attempted, not batched at the end.
- `ToolAdapter.write`'s signature and its `schema.parse` trust boundary are untouched — assert the
  existing write tests pass unedited.
- A patch with `[]` for a group writes nothing for that group and deletes nothing.

## Task 14 — The three scorers

**Files:** `spikes/extraction-snuggpro/score.mjs` and its tests.
**Depends on Tasks 10 and 13.**

**Intent.** Three metrics, because three failure modes fail independently. One number here would
repeat revision 4's defect in a new place — a run can emit the right instance count and still put the
furnace's identity and the AC's ducts in one element.

- **Enumeration** — predicted against true count per group, reported **with direction**, so over- and
  under-segmentation are never averaged into each other.
- **Eligibility** — was each mentioned-and-excluded component excluded, and for the stated reason.
- **Attribution** — bipartite-match predicted to true instances by maximising leaf agreement, then
  score leaves within matched pairs. **Permutation-insensitive by construction.** Unmatched report
  separately: a predicted instance with no match is a fabrication; a true instance with none is a
  miss.

**`readLeaf` must be updated first.** `score.mjs`'s existing path reader splits on `.` and indexes
`model[group][leaf]` — exactly two segments. Instance paths have three, and the middle one is an
instance key. Every metric below reads through it, so this is not a detail of the new scorers but a
precondition for all three.

**Must-fail tests** (the scorer's own mutation tests, as `score.test.mjs` already does):

- A run emitting the correct count with fields swapped between instances scores **badly on
  attribution** while scoring perfectly on enumeration. This is the defect the whole task exists to
  measure; if one metric hides it, the split has failed.
- The same two instances in the opposite order score **identically** — permutation-insensitivity,
  asserted rather than assumed.
- A fabricated instance and a missed instance are reported separately, not netted to zero.

## Task 15 — The review card: instances, and the empty-group affordance

**Un-skip what you unblock.** `skip-inventory.test.ts` records five tests as yours — three in

- **Grouping by instance as well as by resource**, derived generically from the path — the card must
  not know that `hvac` specifically is a collection.
- **The group-level "none described — add one" affordance** for a present-but-empty collection
  (§10.1). This is what replaces the deleted placeholder, and it is the only thing standing between
  an empty group and silence. Without it, dropping the placeholder is a regression rather than a fix.

`addInstance` / `removeInstance` / per-leaf edit are the whole basis (§7.1). Split and merge are
compositions over it and are the host's business, not the hook's.

**Must-fail tests.**

- A two-instance group renders two labelled instance sections, and a leaf edit in the second lands on
  the second — a card that renders both but writes to the first passes a naive check.
- A present-but-empty collection renders the group with the add affordance, not nothing.
- Removing an instance leaves the other instances' entered values in place. This is Task 7's stable
  keys observed from the outside, and it is the failure a user would actually notice.
- The submit gate blocks on an unactioned **required** leaf in any instance, including the second.
  This is the half of Task 8 that cannot live in core, because `resolveReview` never reads
  `ReviewField.required`.
- The submit gate still blocks on an ungrounded leaf in **any** instance, not just the first.

## Task 16 — The strategy ladder

**Files:** the tier-2 and tier-3 extractors in `packages/ribo-extractor-openai/src/`, and the
composition wiring.
**Depends on Task 10.**

**Intent.** This is what the merged arbitration work exists for, and without it that increment has no
consumer. Extraction design §6:

| Tier | Strategy                                        | Isolation                                 |
| ---- | ----------------------------------------------- | ----------------------------------------- |
| 1    | Inventory → scoped per-instance fills (Task 10) | structural — one slot per call            |
| 2    | Per-group call, model emits an array            | prose rules only                          |
| 3    | Per-group flat singleton (today's behaviour)    | none — cannot represent a second instance |

Compose them with `fallbackExtractor` and an arbiter. Tier 3 is on the ladder deliberately: for an
auditor offline in a basement, a single-instance record may beat no record — and **that judgement is
the host's, made through the arbiter's exhaustion call, not the SDK's.**

`terminalFallsThrough` already falls through on a `SchemaParseError`, which is the likeliest tier-1
failure since the roster is a response shape no model has been asked for before.

**Must-fail tests.**

- A tier-1 schema-parse failure falls through to tier 2 and the extraction still returns.
- `usage.strategy` names the tier that produced the result. Without it a degraded run is
  indistinguishable from a clean one, and Task 14's numbers become uninterpretable.
- Tier 2 emits arrays — it must not silently be tier 3 under another name, which is the one way this
  ladder could reintroduce the defect while looking like resilience.
- An arbiter that declines tier 3 at exhaustion throws, and the relay's `dead` handling classifies it
  exactly as it would with no ladder in the path.

## Sequencing

```

3 ─┘   │                     └──→ 15
4      └──→ 9 ─→ 10 ─→ 16
                  └──┐
13 ──────────────────┴─→ 14
```

**Tasks 7 and 8 are serialised on purpose**, not by dependency of logic: both edit `review.ts`, and
parallel work in one file is the collision this project has already paid for once.

Tasks 1–4 are independent and can run in parallel. Task 13 is manual and should start immediately,
because it gates all measurement and nothing else gates it.

**Task 7 is the riskiest**, and its gate is the removing-an-instance test — that is where revision
4's renumbering defect lives, and it is the one place a plausible implementation is silently wrong.
**Task 11 is the most consequential**, because its must-fail test is what stops the auto-link
returning.

**One distinction is deliberately not tested, and saying so is the point.** Design §7.1 notes that on
a **linked** instance, rejecting every leaf means "leave the existing record untouched" while removing
means "DELETE" — opposite instructions. No task tests that divergence, because §10.4 makes removal
usually a field value (`hvacUpgradeAction: "Remove a system permanently"`) rather than a DELETE, and
DELETE is reserved for an explicit human "this record should not exist". The divergence becomes real
only when that explicit action ships. Recorded so a later reader knows it was scoped out rather than
missed.

Run `./check.sh` once after Tasks 12, 15 and 16 — the last of the code tasks. Tasks 13 and 14 are measurement, not gates, and the acceptance
gate stays manual and outside CI.
