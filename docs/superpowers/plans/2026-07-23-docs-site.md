# Docs Site + OSS Front Door — Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** make Ribo read like a real open-source project — a front door a newcomer can land on, and a docs site that explains the pipeline and the pluggable seams. The internal docs (`docs/implementation/*`, `docs/superpowers/*`) are strong but written inward; this repackages the good parts outward.

**Decisions (locked with the user):**

- **Tooling: VitePress.** Vite-native (same family as the Vite 8 / Vitest 4 / pnpm stack), static output, and what Vite/Vitest/Vue/Rollup themselves use — so it looks the part with near-zero new toolchain.
- **License: MIT.** Copyright holder `AZX-PBC`, year 2026.
- **API reference is GENERATED, narrative is hand-written.** TypeDoc (`typedoc-plugin-markdown` + a VitePress theme) points at each package's public `index.ts` barrel and emits the Reference section from the TSDoc already in the code. Narrative pages are authored by hand. Neither half does the other's job.
- **Static + host-agnostic.** `docs:build` emits a static site deployable on Helix _or_ anywhere. Base path configurable so a subpath deploy works.
- **Internal process docs stay internal.** `docs/superpowers/**` (plans, specs) and `docs/open-questions.md` are `srcExclude`d from the public build. The `docs/implementation/*` findings are _repackaged_ into Deep Dives, not dumped.

## Content architecture

- **Home** — what Ribo is, the pitch, quick links.
- **Guide** — Introduction / why Ribo; Getting Started (install, run the playground); the core loop (capture → transcribe → extract → review → write) and the offline-first outbox model.
- **Capabilities** (the pluggable seams) — Transcription (on-device WASM / managed STT), Extraction (the `Extractor` design; single-shot / planned / managed; providers), Adapters (writing a `ToolAdapter`).
- **Offline-first** — the service worker, storage & eviction, the `/ort/` runtime-cache story.
- **Deep dives** — repackaged findings: feasibility, the measured transcription numbers (`14`), the Snugg Pro data model (`12`).
- **Reference** — GENERATED per-package API (ribo-core, -adapter-snuggpro, -transcriber-ondevice, -ui).
- **Design & Contributing** — the D1–D10 decisions, the conventions, the "am I done?" signal (`check.sh`).

## Global Constraints

Everything in [`AGENTS.md`](../../../AGENTS.md) applies, plus:

- **Do not break `check.sh`.** Docs build/generate are their own scripts (`docs:dev`, `docs:build`, `docs:api`), not part of the code gate. A link/build check may be added later, kept separate.
- **Accuracy over marketing.** Every quick-start command, API name, and capability claim must be true against the current code — no aspirational features. Where something is deferred (write-back on A1, iOS out of scope), say so.
- Docs tooling deps catalog-pinned exact, in the right manifest (a `docs` workspace or root devDependencies).

## Definition of done

- `pnpm docs:dev` serves the site; `pnpm docs:build` emits a static site deployable on Helix or anywhere.
- The Reference section is generated from the packages' TSDoc and regenerates on build.
- Root README, per-package READMEs, `CONTRIBUTING.md`, and an MIT `LICENSE` exist and are accurate.
- Internal plans/specs are excluded from the public build.
- `check.sh` green.

## Deliberately NOT here

Hosting/CD wiring to a specific Helix route (kept host-agnostic — static output is the deliverable), versioned/multi-release docs, i18n, and a search backend beyond VitePress's built-in local search.
